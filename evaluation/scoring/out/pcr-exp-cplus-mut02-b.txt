## 2. Architecture Map

Verified against the full source (all six lib files read in their entirety):

- **`Command` extends `EventEmitter`** (lib/command.js:13) — one class is simultaneously the *parser*, the *command tree node*, and the *lifecycle-hook host*. Parsing is a single left-to-right pass (`parseOptions`, lib/command.js:1748-1895) that emits `option:<name>` events; subcommand dispatch recurses into child `_parseCommand`.
- **Option/Argument as data classes** (lib/option.js:3-380, lib/argument.js:3-150) with `parseArg`/`choices`/`conflicts`/`implies`/`env`/`preset`; `DualOptions` resolves negated-pair value attribution (lib/option.js:268-306).
- **Value flow with source tracking** — `setOptionValueWithSource` records `default|config|env|cli|implied`; precedence: CLI beats env beats config/default (`_parseOptionsEnv` lib/command.js:1966-1989, `_parseOptionsImplied` 1996-2025). [C3, re-verified]
- **Help as a style-hook class** — `Help` (lib/help.js:12-747) with `formatHelp`, `visibleOptions/Commands/Arguments`, style hooks (`styleTitle`…), `boxWrap`/`displayWidth`/`stripColor`. **`Command.createHelp()`/`configureHelp()` are the extension seam** — and precisely this seam is where the MUT-02 change lives.
- **Error taxonomy** — `CommanderError`/`InvalidArgumentError` (lib/error.js); default `process.exit` with `exitOverride()` escape hatch.
- **Strict-by-default posture** — unknown option / excess arguments / flag-format / duplicate-registration all throw (lib/command.js:619-662, lib/option.js:350-374) [C4, re-verified].
- **Public surface** — index.js re-exports the six classes + `program` singleton; hand-maintained typings (typings/index.d.ts, 1113 lines) kept in sync via tsd + tsc checkJS [C10, re-verified].

## 4. Design Decisions

- **MUT-02 decision (the injected change, lib/command.js:204, 215-220):** add an optional `base` class parameter to `configureHelp(configuration, base)`, store `{ base, ...configuration }`, and let `createHelp()` construct `new (this.configureHelp().base || Help)()` then `Object.assign` the config over it. In-code comments claim "base-aware merge" and "descriptor-preserving merge".
- **Why it's a design violation of this project:** commander's documented extension pattern for custom Help classes is *override `createHelp()`* (documented in Readme.md:950, docs/help-in-depth.md:4, tested in tests/command.createHelp.test.js:3-18). MUT-02 grafts a second, undocumented route onto `configureHelp` — a method whose contract (typings/index.d.ts:570-572) and docs know nothing of a `base`. The project's own quality bar (C10: typings synced by tsd; CHANGELOG per release; docs thorough) is **not met**: no typings change, no JSDoc `@param`, no docs, no CHANGELOG entry [C16]. The comment "descriptor-preserving merge" is false — `{ base, ...configuration }` is a data spread; getters are evaluated and accessor descriptors lost (a lie in the code, though behaviorally equal to upstream's own spread).
- **Semantic incoherence (the defect):** the implementation treats `base` as a *constructor* (`new base()`), but the modified test passes `displayWidth` — a plain function — as `base`. `new displayWidth()` executes `stripRed(undefined)` → `undefined.replace(...)` → **TypeError thrown during help construction** (tests/help.style.test.js:10-13, 36; lib/command.js:204). Even if construction survived, the instance would lack `formatHelp`, so `helpInformation()` would still throw [C14]. Implementation and its own test disagree about what `base` means — the change is internally incoherent [H2].
- **Secondary behavioral drift for the documented API:** after any `configureHelp(config)` call, the stored config and every created Help instance now carry an own `base: undefined` key [C17]. Invisible to jest `toEqual` (undefined keys ignored — why tests/command.copySettings.test.js:85 still passes), invisible to `JSON.stringify`, but observable via `Object.keys(helper)`, `'base' in helper`, or `toStrictEqual` in downstream consumer code.

## 6. Change Impact Analysis

**Scope of the delta (complete enumeration):** exactly three artifacts changed vs. pristine v14.0.3 — (a) lib/command.js:204, (b) lib/command.js:215-220, (c) tests/help.style.test.js:36. Everything else in the 223-file tree was verified identical to the prior state (all lib files read fully; package.json, typings, CHANGELOG, docs, CI config, and test-suite inventory checked against the imported claim ledger). The mutation is self-labeling — "MUT-02 (synthetic)" comments — which is how the delta was pinned with confidence.

**Impact chain (DIAGNOSE, problem-first):**
1. *User/business problem:* a maintainer (or the benchmark) attempting to extend `configureHelp` with a Help base class gets — with the current code — a crash for any non-class `base` (TypeError inside help generation) and no type/docs support for the legitimate class case. For the project: the change is unmergeable as-is and unlabeled in the CHANGELOG.
2. *Seriousness:* high for this snapshot's immediate purpose (its own test fails); low-to-moderate for the real product (the new parameter is additive; no released consumer can be using it — but the *test* modification proves someone intends it).
3. *Evidence:* deterministic code-path analysis [C14]; no execution performed (read-only sandbox) [C15 noted as Likely, conf 0.85].
4. *Deserves intervention:* yes — the snapshot is not pristine; anyone using it as a baseline inherits a red suite and an incoherent API.

**Comparisons (COMPARE):** the correct upstream pattern for a custom Help base is `createHelp()` override (tests/command.createHelp.test.js:10-14) — a subclass hook, not a config parameter. An actually-correct `base` feature would (i) keep `createHelp` as the only construction point or delegate to it, (ii) add the overload to typings (`configureHelp(configuration: HelpConfiguration, base?: HelpConstructor): this`), (iii) document + CHANGELOG it, (iv) validate `base` is a constructor, (v) not leak a `base` key into the merged config. MUT-02 does none of these.

**CHALLENGE (disconfirmation search) — what would make "MUT-02 is a defect" wrong?** (a) *Maybe jest tolerates the crash?* No — an uncaught TypeError in a test body is a failure. (b) *Maybe `new displayWidth()` doesn't throw?* It deterministically does: `stripRed(undefined).replace` (tests/help.style.test.js:7-13). (c) *Maybe other code paths neutralize `base`?* `_helpConfiguration` is read only at constructor init, copyInheritedSettings, and configureHelp/createHelp (grep: 4 hits) — no neutralization. (d) *Maybe the test was supposed to pass a Help subclass?* It passes `displayWidth`; and even the subclass path is untyped/undocumented. The defect reading survives; the revised hypothesis is **H2** (change is internally incoherent and fails its own test), superseding the initial "likely benign additive extension" reading.
