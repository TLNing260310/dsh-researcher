**Parse pipeline** (all in `lib/command.js`): `parse()/parseAsync()` → `_prepareForParse()` (save/restore state, :1131) → `_prepareUserArgs()` (argv slicing, electron/eval/node detection, :1005) → `_parseCommand()` (:1554) → `parseOptions()` (token loop: literals, short combos, `--x=y`, negative-number detection, positional/pass-through modes, :1752) → option listeners (`addOption` registers `option:name` handler → `_callParseArg`, :696-727) → subcommand dispatch (`_dispatchSubcommand`/`_executeSubCommand` spawn, :1356/:1206) → argument processing (`_processArguments` → `_callParseArg` per value, :1432) → hooks chain (`preSubcommand`/`preAction`/`postAction`, :1485-1553).

**Error pipeline** (the mutated seam): all user-facing failures converge on `error(message, {code, exitCode})` (:1944) → writes via `_outputConfiguration.outputError`, optionally shows help (`showHelpAfterError`) or suggestions (`showSuggestionAfterError`) → `_exit` (:533) → `_exitCallback(new CommanderError(...))` if `exitOverride()`, else `process.exit()`. `_callParseArg` (:599) is the adapter that converts a user's `InvalidArgumentError` from custom `parseArg`/choices into this pipeline, prefixing the contextual message (`error: option '…' argument '…' is invalid.` / `error: command-argument value '…' is invalid for argument '…'.`).

**Three entry points into the mutated function** — all affected: option CLI values (:706), option env-var values (:731-733 → :706), command-argument values (:1438).

**Help pipeline**: `helpInformation()` (:2454) → `createHelp()` (overridable factory) → `Help.prepareContext`/`formatHelp` (help.js:29/:443) with pluggable `style*` hooks, width/wrap calculations, grouping, color stripping. Version/help exits use the same `_exit` contract (`commander.version`, `commander.helpDisplayed`, :2210/:2696).

## 3. Critical Components

1. **`Command._callParseArg`** (lib/command.js:599-613) — **the mutation site.** Conversion point for invalid-argument errors; the only place `commander.invalidArgument` is consumed (:603).
2. **`CommanderError` / `InvalidArgumentError`** (lib/error.js:4-36) — the stable error-code carriers; `InvalidArgumentError` hard-codes `code = 'commander.invalidArgument'`, `exitCode = 1` (:31). Unchanged by the mutation.
3. **`Command.error`/`_exit`/`exitOverride`** (lib/command.js:1944-1961, 508-554) — the documented error contract (Readme.md:1110-1131: "The default override throws a `CommanderError`").
4. **`parseOptions` + option/argument value handlers** (:1752, :696-727, :1432-1474) — where user values flow into `_callParseArg`; includes negative-number detection, `--` literal handling, combined short flags, variadic collection.
5. **`Option`/`Argument` parseArg + choices validation** (option.js:181, argument.js:98) — the producers of `InvalidArgumentError`; `choices()` installs a validating parseArg, so choice mismatches also flow through the mutated seam.
6. **`Command._parseCommand`** (:1554-1645) — orchestration; notably has **no try/catch** around `_processArguments`/`parseOptions`, so the raw error escapes straight to the caller of `parse()`.
7. **`Help`** (help.js) — overridable help generator; independent of the mutation but part of the error UX (`showHelpAfterError` renders through it).
8. **`suggestSimilar`** (suggestSimilar.js) — Damerau–Levenshtein, similarity threshold >0.4, used for unknown option/command suggestions; independent of the mutation.

## 4. Design Decisions

- **Stable error codes as semver contract** — codes like `commander.invalidArgument`, `commander.missingMandatoryOptionValue`, `commander.unknownOption` are public API, pinned by tests (exitOverride.test.js:5-7) and documented in CHANGELOG (e.g., CHANGELOG.md:461 documents the v7 rename `commander.invalidOptionArgument` → `commander.invalidArgument`). *This is the constraint the MUT-05 injection targets.*
- **Single error funnel** — every failure goes through `error()` → `_exit()` so output, help-after-error, suggestions, and exit/override behavior stay consistent.
- **`_callParseArg` as the adapter** — user `parseArg` may throw `InvalidArgumentError` (documented pattern, Readme.md:470-478) or anything else; the adapter prefixes context, converts to the funnel, and lets non-invalid errors propagate raw (plain errors must NOT become CommanderError — pinned by argument.custom-processing.test.js:168-187).
- **Override factories** (`createCommand/createOption/createArgument/createHelp`, `.command()` inheritance via `copyInheritedSettings`) — extensibility without subclassing.
- **Event-driven option values** (`option:name` / `optionEnv:name` events) with `setOptionValueWithSource` provenance tracking (default/env/cli/implied).
- **Dual-package CJS/ESM + hand-written typings**, checked by tsd + tsc under `checkJs` (tsconfig.json:17-18) — the "type safety without TypeScript" decision.
- **Executable subcommands** spawn with node-flag forwarding (`incrementNodeInspectorPort`), extension probing (.js/.ts/.mjs/.cjs), and signal relay (:1206-1350).
- **Help as data** — `Help` methods are static-in-style for override; width/wrap/color all pluggable.

### 6.2 Previous assumptions that no longer hold

1. **"Invalid-argument failures always flow through `this.error()` and exit via `_exit`"** (true in t0 and MUT-04) — **no longer holds**: in MUT-05 the raw `InvalidArgumentError` escapes `parse()`; default mode yields an uncaught exception; override mode yields an unpiped error; help-after-error/suggestion never trigger.
2. **"Error codes are produced exclusively by `error()`/`CommanderError` and the set of codes is closed"** — violated: `commander.invalidArgumentValue` appears from nowhere; the semver-stable code set is silently extended.
3. **"Plain `Error` throws from custom `parseArg` propagate raw"** (pinned by argument.custom-processing.test.js:168-187 and exitOverride.test.js:448-460) — **no longer holds** for code-less errors: they are now wrapped as `CommanderError('commander.invalidArgumentValue')`.
4. **"The snapshot passes its own CI"** (assumption carried from the pristine series) — **no longer holds**: eslint `no-unreachable`/`no-unused-vars` fail; 6 tests fail.
5. **"MUT-04's area (excess-arguments timing) is the current deviation"** — no longer holds: MUT-04's injection is gone (restored to t0); the deviation moved to the error-code pipeline. (Each snapshot is an independent injection over the same t0 — MUT-05 does not *contain* MUT-04's change.)
6. **Held assumptions confirmed**: tests are the untouched spec; docs/CHANGELOG/typings unchanged; `InvalidArgumentError` code string itself unchanged — the mutation attacks the *handling* of the code, not its production.

- **Repair surface**: exactly one function, `_callParseArg` (lib/command.js:599-613) — restore the t0 form: reinstate `this.error(message, { exitCode: err.exitCode, code: err.code });` in the `commander.invalidArgument` branch; delete the `// MUT-05 (synthetic)` comment, the `else if` branch, and the unreachable `this.error`. No other file changes; no docs, typings, or tests change.

## 7. Decision Memo

**Context.** This snapshot is commander.js v14.0.3 plus one synthetic, self-marked mutation (`compatibility_constraint`, candidate `error code: commander.invalidArgument`). The injected change sits at the single chokepoint that turns a user's `InvalidArgumentError` into commander's standardized error pipeline, and it replaces that conversion with a comment, a raw rethrow, a fabricated error code, and dead code. It violates the project's own documented, semver-stable error contract (exitOverride.test.js:5-7; Readme.md:1110-1131; CHANGELOG.md:461), degrades end-user CLI error UX to uncaught stack traces, silently changes plain-Error propagation, and breaks the project's lint gate.

**Corrosion, not evolution** (CHALLENGE verdict): the marker comment admits synthetic origin; the unreachable statement and unused variable could not pass the project's own CI, which every upstream PR must pass; four independent siblings of the same t0 commit agree on the pristine form; no CHANGELOG entry, doc, or test references the new code. Every disconfirmation attempt (upstream source? adapted tests? intentional feature? different mutation site? changed `InvalidArgumentError` code?) failed; the evidence is uniform.

**Classification:**
- **BUILD** — Repair: restore `_callParseArg` (lib/command.js:599-613) to the t0 implementation. High confidence, near-zero risk, verified by the untouched 95-file suite + lint.
- **DON'T BUILD** — anything else: no feature work, no "improvement" to keep the `else if` (the pristine suite pins the opposite behavior; keeping it would require changing the spec — forbidden here), no test changes, no docs changes, no dependency changes.
- **INVESTIGATE** — one residual item, verification-only: execute `npm test` and `npm run check:lint` (impossible in this read-only session) to confirm the predicted 6 test failures and 2 lint errors; expected counts per R5/R4.

**Verification net for the repair** (for Plan Mode): full jest suite (expect 0 failures after repair), `npm run check:lint` (expect clean), `npm run check:type` + `check:format` (expected unaffected). The repaired function must be byte-equivalent in behavior to MUT-01/02/04/06 `lib/command.js:599-609`.
