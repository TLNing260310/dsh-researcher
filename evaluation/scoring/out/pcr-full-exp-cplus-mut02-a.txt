## (4) Design Decisions

**The mutation, exactly** (base → MUT-02, `lib/command.js`):

```diff
  createHelp() {
-   return Object.assign(new Help(), this.configureHelp());
+   return Object.assign(new (this.configureHelp().base || Help)(), this.configureHelp()); // MUT-02 (synthetic): base-aware merge
  }
  configureHelp(configuration) {
+   // MUT-02 (synthetic): optional base-class parameter + descriptor-preserving merge.
    if (configuration === undefined) return this._helpConfiguration;
-   this._helpConfiguration = configuration;
+   this._helpConfiguration = { base, ...configuration };
    return this;
  }
```

**Five contract changes, in one change** (the "design decision" the mutation encodes):

1. **New, undocumented, untyped second parameter** `base` — a "custom Help base class" feature. Dead on arrival for TypeScript consumers (overloads forbid it, `index.test-d.ts:521-529`); discoverable only by reading JS source.
2. **Config is now copied, not aliased** — `configureHelp(config)` used to store the caller's object by reference; later mutation of `config` was reflected. Now the getter returns a *different* object. (Note the irony: upstream deliberately fixed the mirror-image aliasing bug for `configureOutput` in 14.0.0, `CHANGELOG.md:56`; it did **not** apply that to `configureHelp`.)
3. **Spurious own key** — the stored config (and therefore the `configureHelp()` getter, and every `Help` instance via `Object.assign`) now always carries `base: undefined` when no base is given. Invisible to Jest's `toEqual` (ignores `undefined`), visible to `Object.keys`, `'base' in cfg`, spreads, and object enumeration.
4. **`base` became a live control key** — under upstream semantics a `base` key in a user config was inert data; under the mutant, `createHelp()` executes `new config.base()`. A non-constructor value → `TypeError: … is not a constructor` at help-display time; a constructor → silently swapped help class, invoked **with zero arguments**.
5. **`createHelp()` calls `configureHelp()` twice** — harmless for the stock implementation, but a subclass overriding `configureHelp` with side effects now runs twice per help render.

**Why this is corrosion, not evolution** (corrosion question): the conventions violated are (a) public API changes ship with typings + docs + CHANGELOG + tests (stated in `PULL_REQUEST_TEMPLATE.md`: "There are a lot of forms of documentation which could need updating… TypeScript typings, JSDoc documentation, tests, README, examples"); (b) `configureHelp` stores by reference; (c) `createHelp` instantiates the stock `Help` class only. All three reasons still hold for a package with this adoption scale — so the deviation is a contract violation, not a legitimate feature. This is confirmed by the benchmark's own classification (`kind: api_contract`).

## (6) Change Impact Analysis

**What changed vs. the previous snapshot (base `commander.js/workspace`, same v14.0.3):** exactly one file, `lib/command.js`, two hunks — `createHelp()` (line 204) and `configureHelp()` (lines 215-220). Everything else is byte-identical: 6 lib files, `index.js`, `esm.mjs`, `package.json`, `package-support.json`, `jest.config.js`, both typings files, all 134 test files, all 9 docs, all 45 examples, configs, CI. Verified by three independent full-tree diff agents plus my own reads.

**Previous assumptions that no longer hold** (C13):

1. *"`configureHelp(config)` stores the config object by reference"* — **false now**: a shallow copy is stored; post-call mutations of the caller's object are invisible.
2. *"`configureHelp()` returns exactly what was stored"* — **false**: it returns `{ base: undefined, …config }` — an extra own key.
3. *"`createHelp()` always instantiates `new Help()`"* — **false**: it instantiates whatever `config.base` is, when truthy.
4. *"A `base` key in a help configuration is inert data"* — **false**: it is now live code (constructor).
5. *"`configureHelp` takes exactly one argument"* — **false in JS** (two accepted), **still true in typings** — the JS/TS contracts now disagree.
6. *"`Help` instances carry only documented data properties"* — **false**: a stray own `base` property appears.
7. *"The tree passes `npm run check`"* — **likely false** (prettier; tsc TS2339) — while `npm test` stays green.

**Blast radius:** zero impact on the parsing/execution core (options, arguments, subcommands, hooks, env/implied values all untouched); the impact is confined to the help-configuration contract — but that contract is public, typed, and documented, and the change is *silent* (green suite), which is precisely the dangerous combination: every locally-reasonable step (the change "looks like" a feature, tests pass) adds up to a globally wrong contract (R6).

## (7) Decision Memo

**Question asked:** what is this project, what changed vs. the previous snapshot, and what (if anything) should be done.

**Answer:** this is a benchmark mutation snapshot — Commander.js v14.0.3 with a single self-tagged, `api_contract`-classified mutation injected into the public `configureHelp`/`createHelp` API. The mutation is feature-shaped but contract-corrosive: it adds an undocumented, untyped constructor-switch parameter; breaks config aliasing and getter purity; can crash help rendering on a non-constructor `base` value; and is invisible to the entire shipped test suite and to `npm test`.

**Findings classification:**

- **BUILD — F1: revert the two hunks to upstream semantics** (restore `configureHelp(configuration)` storing by reference, and `createHelp()` instantiating `new Help()`). The deviation is identified with C3-tier evidence (self-tag, benchmark metadata, base-snapshot comparison); the fix is a mechanical restoration of the base's 6 lines. This is the only change this snapshot warrants.
- **INVESTIGATE — F2: test-suite blindness.** No shipped test pins the contract (reference identity of stored config, exact key set, `base` inertness). Whether to add such contract-pinning tests is the user's/benchmark's call — for the benchmark, hidden tests presumably cover it; for upstream, this is a real (pre-existing) coverage gap worth knowing about. Not a development action from this session.
- **DON'T BUILD — keep the `base` feature as-is, or ship it as a real feature.** As-is it is half-wired (no typings/docs/tests/CHANGELOG; zero-arg constructor invocation; config-key collision with the reserved `base`). Shipping it properly would be a full upstream feature project — out of scope for a mutation snapshot, and contrary to the benchmark's intent.
- **DON'T BUILD — anything else.** No other part of the project changed; there is nothing else to fix.

**Cost/benefit of the recommended action:** the revert is ~6 lines, zero risk to the parsing core, and restores the documented + typed + tested contract; the cost of *not* acting is a silent API-contract break exported as if it were v14.0.3.

**Confidence statement:** the location and content of the change are **Known** (0.97–1.0); the test-suite passivity is **Likely** (0.9 — semantic analysis, not execution, because the sandbox is read-only); the quality-gate failures are **Likely** (0.75–0.9 — prettier/tsc not executable here); live upstream byte-verification was impossible (web_fetch has no registered provider), compensated by the pristine same-version base snapshot.
