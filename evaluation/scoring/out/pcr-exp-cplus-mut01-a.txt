# Project Cognition Report — commander.js @ MUT-01

**Runtime Proof** — Researcher Runtime Certificate, Run #2: **Overall SAFE** (preset=researcher-deep; sandbox=read-only PASS; approval=never PASS; write/edit=refusing stubs PASS; shell surface: git_read only PASS; checkpoint PASS; replay folds deterministically). Depth: **DEEP** (all eleven moves, frozen Phase A condition D002). All evidence below is read-only derived; nothing was executed or modified.

**Executive finding (one paragraph).** This workspace is **commander.js v14.0.3** (baseline commit `bf35c5f9`, cut 2026-02-01) with exactly **one injected source change**: in `lib/command.js`, `restoreStateBeforeParse()` no longer throws the documented error on repeated `parse()` when `storeOptionsAsProperties` is enabled — it now *silently sets `_storeOptionsAsProperties = false`* and continues (lib/command.js:1158-1174, marker comment at :1159). The CHANGELOG, typings, tests, docs, and every other file are unchanged. The change is **corrosion dressed as a feature**: it violates a documented, tested, deliberately-breaking upstream contract (v13.0.0, #2299), breaks the existing test `tests/command.parse.test.js:412`, silently mutates user configuration, leaks stale option properties onto the Command instance, and changes the action-handler argument shape between parses. Verdict: **revert**; do not build the "feature".

## 3. Critical Components

1. **Parse lifecycle + save/restore machinery** (lib/command.js:1090-1174) — the only changed code. `_prepareForParse` gates every parse; the guard inside `restoreStateBeforeParse` is the *entire* protection for the legacy storage mode across repeated parses. **This is where the defect lives.**
2. **Option-value storage duality** — property mode (`this[key]`) vs `_optionValues` (lib/command.js:925-961, 1902-1917). Both modes are load-bearing; the mutation silently flips the mode mid-lifecycle.
3. **Action handler contract** (lib/command.js:556-572) — the "options" parameter is `this` in property mode, `opts()` otherwise; the mutation makes the two parses disagree.
4. **Error/exit surface** (lib/error.js; lib/command.js:1940-1958) — error codes (`commander.invalidArgument`, `commander.missingMandatoryOptionValue`, …) are a documented compatibility surface (cf. sibling mutations MUT-05/06 targeting exactly this).
5. **Typings** (typings/index.d.ts:851,859) — the API contract for TS consumers; unchanged, so static checks still pass while runtime behavior diverges.
6. **Test suite** (~120 jest files + tsd) — unchanged; `tests/command.parse.test.js:412` is the single behavioral test that pins the mutated contract and therefore **fails** under MUT-01.

## 6. Change Impact Analysis

### 6.1 Delta vs the previous snapshot (baseline `commander.js` @ `bf35c5f9`)

File sets are identical (223 source paths; MUT-01 adds only the untracked harness artifacts `evaluation/scoring/out/_probe/*`). Cross-checked byte-equality: `package.json`, `CHANGELOG.md` (incl. :74, :85), `typings/index.d.ts` (:851, :859), `typings/index.test-d.ts` (:374-375), `tests/command.parse.test.js` (incl. :412-418), and `lib/command.js` everywhere except the mutated block. The **only** source delta (C04, Likely, conf 0.85 — exhaustive byte-compare not performed, but every targeted comparison matched and a single mutation marker exists):

```diff
  restoreStateBeforeParse() {
-   if (this._storeOptionsAsProperties)
-     throw new Error(`Can not call parse again when storeOptionsAsProperties is true.
- - either make a new Command for each call to parse, or stop storing options as properties`);
+   // MUT-01 (synthetic): repeated parse is now allowed under storeOptionsAsProperties.
+   if (this._storeOptionsAsProperties)
+     this._storeOptionsAsProperties = false;
```

### 6.2 Previous assumptions that no longer hold

1. **"Repeated `parse()` with `storeOptionsAsProperties: true` throws"** — no longer; it silently continues with the mode flipped off.
2. **"Implementation matches the documented contract"** (CHANGELOG.md:85, *Breaking* #2299) — no longer; docs still promise the throw.
3. **"The test suite passes"** — no longer; at least `tests/command.parse.test.js:412` fails (C06, Likely, conf 0.9).
4. **"`storeOptionsAsProperties()` is a sticky configuration setting"** — no longer; the second parse silently discards the user's explicit choice.
5. **"Action handlers receive a consistent options argument across parses"** — no longer; parse 1 passes `this`, parse 2 passes `opts()`.
6. **"Option-value storage location is stable across parses"** — no longer; storage flips from instance properties to `_optionValues`, leaving stale properties behind.
7. **"A comment in the code is evidence of intended behavior"** — never valid, now actively dangerous: the marker comment at lib/command.js:1159 is the *only* in-code authority for the new behavior, and it contradicts the CHANGELOG, the typings era, and the tests. (For this harness the comment is honest about being synthetic; in a real codebase a similar comment would be indistinguishable from author intent.)

### 6.3 Impact chain

First parse (property mode): `setOptionValueWithSource` writes `this[key]`; saved state holds only `{_name, _optionValues, _optionValueSources}` (defaults). Second parse: `restoreStateBeforeParse` flips mode to false, restores `_optionValues` to pre-parse defaults, and **never removes** the `this[key]` properties from parse 1. Thereafter `opts()` (:1903) and `getOptionValue` (:926) read `_optionValues`, the action callback receives `opts()` instead of `this`, and the user's legacy configuration is gone with no error, no warning, and no migration path. The change is locally "helpful" (one less error) and globally corrosive (predictability — the library's core value — is silently traded away).

## 7. Decision Memo

**Question:** Should MUT-01's change to `restoreStateBeforeParse()` be kept, reverted, or evolved?

**Analysis (DIAGNOSE → CHALLENGE):** The change presents as a feature ("repeated parse is now allowed") but fails every test of legitimate evolution: (a) it contradicts a *deliberately breaking* upstream decision (v13.0.0 #2299) whose rationale still fully holds — property-mode writes cannot be unwound, and the action-signature/storage-view duality makes mixed-mode parsing unsound (C08-C10); (b) it updates no contract surface — not CHANGELOG, not docs, not typings, not tests (C11-C12); (c) it breaks the existing suite (C06); (d) it silently mutates user configuration — the worst failure class for a library whose value is strict predictability (Readme.md:73 "Commander is strict"). Disconfirmation search: the only reading that would make this "evolution" is treating the code comment as authoritative — disproven by the unchanged CHANGELOG/test/typings, and by the harness's own metadata (`kind: api_contract`, mutation MUT-01). **Verdict: CORROSION.**

**Tradeoffs:** Reverting is a 3-line change restoring a known-good, tested contract — minimal cost, maximal certainty. Keeping the change invites a full redesign (stale-property cleanup, mode-stability guarantees, doc/typings/test updates, migration notes) to fix an unsound idea with **no evidence of user demand** — upstream maintainers explicitly excluded this combination, and the sibling mutations (MUT-02..06) show this corpus evaluates *detection of* such defects, not their adoption. "Improve other things while we're here" is rejected (local optimality ≠ global; the rest of the repo is unchanged and healthy).

**Classification:**
- **BUILD** — Restore the upstream throw in `restoreStateBeforeParse()` (revert the MUT-01 delta). Confidence 0.9.
- **DON'T BUILD** — The "repeated parse under `storeOptionsAsProperties`" feature in any form.
- **INVESTIGATE** — None required for this decision. (Optional follow-up, not blocking: an explicit test for the subclass `save/restoreStateBeforeParse` hook — currently only a tsd type-check exists, a pre-existing coverage gap that this mutation exploited.)
