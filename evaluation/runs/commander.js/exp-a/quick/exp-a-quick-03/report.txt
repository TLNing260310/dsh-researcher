## 1. Project Identity

**What it is.** Commander.js is the de-facto standard framework for building Node.js command-line interfaces — "the complete solution for node.js command-line programs" (Readme.md:8; package.json:4). Version **14.0.3**, MIT-licensed, authored by TJ Holowaychuk, maintained today primarily by John Gee (shadowspawn) with dependabot-driven dependency upkeep (git log: 8247364, e281fe3, fe92dc5).

**Snapshot provenance.** The workspace is a faithful copy of upstream HEAD — commit `bf35c5f` (2026-02-02), clean working tree (git status: empty), two days after the 14.0.3 release (2026-01-31). No local modifications, no forks, no divergence. The 14.0.3 release itself is deliberately minimal: a new release-policy document, a typing clarification, and README readability (CHANGELOG.md:11-21). [C01, C02 — C2/Known]

**Mission.** Provide a declarative, strict, well-documented API for defining options, arguments, subcommands, help, and executable subcommands — so CLI authors never hand-roll `argv` parsing. Value mechanism: *trusted correctness at the parsing layer* — the library's value is that millions of downstream CLIs inherit the same, battle-tested parsing semantics (strictness, error messages, "did you mean" suggestions, help formatting) rather than each implementing their own.

**User & problem.** Users are Node.js CLI authors at every scale — from one-file scripts to multi-command enterprise CLIs. Their problem: parsing CLI arguments is deceptively hard (option combinations, negation, variadic values, negative numbers, subcommand dispatch, help formatting, exit codes). Commander's answer: "You write code to describe your command line interface" (Readme.md:69-71); it handles the rest, strictly — unknown options are errors with suggestions (Readme.md:73, 94-96).

**Current state.** Release 14.x line, Node ≥20 required (package.json:79; breaking change introduced in 14.0.0, CHANGELOG.md:60). Support policy: current line gets all updates; older majors get security-only fixes for 12 months (docs/release-policy.md:10). The project is in **stable-maintenance-plus-incremental-features** mode: majors every ~6 months aligned to Node LTS EOL, features still landing (help groups and unescaped negative numbers in 14.0.0, CHANGELOG.md:47-51). [C08, C12 — C2/Known]

## 2. Architecture Map

**Shape.** A single-file-per-concern CommonJS library, ~4,100 lines of runtime code across six files, zero runtime dependencies (package.json:62-76; package-lock.json:7-29 root entry has no `dependencies` key — only devDependencies) [C03 — C2/Known]:

```
index.js            — public API surface (24 lines): program singleton, create* factories, classes
esm.mjs             — ESM named-export wrapper over index.js (dual-package support)
lib/command.js      — Command class: the parser + dispatcher + public DSL (2,777 lines)
lib/option.js       — Option (declarative flag spec) + DualOptions helper (380 lines)
lib/argument.js     — Argument (positional arg spec) + humanReadableArgName (150 lines)
lib/help.js         — Help class: help-text rendering with style/format extension points (747 lines)
lib/error.js        — CommanderError, InvalidArgumentError (39 lines)
lib/suggestSimilar.js — Damerau–Levenshtein "did you mean" suggestions (101 lines)
typings/index.d.ts  — hand-maintained TypeScript declarations (1,113 lines)
```

**The parse pipeline** (the heart) [C04 — C2/Known]:
1. `parse()`/`parseAsync()` → `_prepareForParse()` (save/restore state for repeat parses, command.js:1127-1133) → `_prepareUserArgs()` (argv convention detection: node/electron/eval/user, command.js:1001-1065).
2. `_parseCommand(operands, unknown)` (command.js:1550-1641) — a dispatch decision tree: subcommand match → help command → default command → action handler (with preAction/postAction hooks) → legacy `command:*` events → help-on-error → unknown-command error.
3. `parseOptions(args)` (command.js:1748-1895) — a single stateful scan loop that classifies each arg as option/operand/unknown, handling `--` literal, variadic option accumulation, short-flag groups (`-abc`), `--foo=bar`, optional values, and negative-number disambiguation. Options are **emitted as events** (`option:<name>`), which the constructor's listeners convert into stored values — this event bus is what makes custom parsing, env vars, and implied values uniform.

**The two dispatch styles.** (a) **Action handlers** — in-process functions chained through promise hooks (`preAction`, `postAction`, `preSubcommand`, `postSubcommand`); (b) **executable subcommands** — child-process spawn with source-extension resolution (`.js/.ts/.tsx/.mjs/.cjs`), legacy script-name prefix fallback, Node inspector port re-increment, signal forwarding, and `process.exit` hand-off (command.js:1202-1346). Both are first-class; this dual model is a core architectural trait.

**Help system** is fully separated into the `Help` class with ~30 overridable methods (visible options/commands, term/description formatting, box-wrapping, ANSI stripping, style functions) (lib/help.js method map; formatHelp at 443-527) [C05 — C2/Known].

**Type story.** JS is type-checked via `checkJs` (tsconfig.js.json), TS consumers get hand-maintained `index.d.ts` verified by `tsd` + `tsc` (package.json:26-27); ESM surface verified at runtime by `tests/esm-imports-test.mjs` [C07 — C2/Known].

## 4. Design Decisions

1. **Zero runtime dependencies** (C03). The library ships with no deps at all — install size and supply-chain trust are product features for a package this widely installed.
2. **CommonJS core + ESM wrapper** (index.js / esm.mjs) rather than dual-authored builds — one implementation, two import surfaces, verified by a dedicated ESM smoke test.
3. **Event-driven parsing** (`option:<name>` emits, command.js:1787-1844). This single mechanism unifies CLI values, env-var values (`_parseOptionsEnv`), and implied values (`_parseOptionsImplied`) — "after cli, so parseArg not called on both cli and env" (command.js:1552).
4. **Strictness by default, leniency as opt-in flags** — unknown options and excess arguments are errors unless `.allowUnknownOption()`/`.allowExcessArguments()` (command.js:837-860); each opt-in is a discrete, documented switch.
5. **Explicit value sources** — `_optionValueSources` tracks default/env/cli per option (command.js:39, 953-983), enabling conflict detection that ignores defaults (command.js:1694-1715) and correct dual-option behavior.
6. **Dual-option value provenance via heuristic** — `DualOptions.valueFromOption` explicitly deduces origin from value equality with the negative preset: "Use the value to deduce if (probably) came from the option" (option.js:301). A documented probabilistic inference, not a bookkeeping guarantee.
7. **Deprecation-first evolution** — nine deprecated features still shipped and documented (docs/deprecated.md:1-21), legacy code paths (`.on('command:*')`, `command:'*'`, `storeOptionsAsProperties`) kept alive inside the hot dispatch path (command.js:1606-1631, 1614-1625) — compatibility over cleanliness. [C10 — C2/Known]
8. **Repeatable parse** — `saveStateBeforeParse`/`restoreStateBeforeParse` (command.js:1141-1174), added in 13.0.0, with an explicit error when incompatible with `storeOptionsAsProperties` (1159-1161).
9. **Release cadence tied to Node LTS** — major bump when Node LTS EOLs; 12-month security window for old majors (release-policy.md:5, 10).

## 6. Change Impact Analysis

For a snapshot of **upstream library HEAD**, "changes" means either (a) hypothetical upstream PRs, or (b) modifications to this workspace. Both are analyzed; the workspace itself is a study artifact, not a codebase we own.

**Highest-blast-radius change surfaces (order matters here):**
1. **`parseOptions` / `_parseCommand` semantics** — any reordering of the dispatch decision tree or the classification loop changes behavior for *every* dependent CLI. Requires the full 109-file suite + the 9-OS CI matrix, plus a deprecation cycle per policy. Only justifiable as a major-version feature.
2. **Help output format** — dozens of `help.*` tests snapshot exact text (help.test.js, helpGroup.test.js…); whitespace/grouping changes ripple into downstream docs and snapshot tests. 14.0.0's help-group feature (CHANGELOG.md:49) shows the acceptable pattern: additive, behind explicit API.
3. **Type declarations** — changes must land in lockstep across `typings/index.d.ts`, `typings/esm.d.mts`, `typings/index.test-d.ts`, with `tsd` green; drift here is the most likely silent failure mode (R3).
4. **Option flag parsing** (`splitOptionFlags`) — already fail-noisy by design (option.js:350-374); any extension (e.g., new flag shapes) must keep that contract or silently accept typos downstream.
5. **`_executeSubCommand`** — OS-behavior surface (spawning, signals, Windows path at 1278-1288); changes need the executableSubcommand.* test set (6 files) and manual cross-platform verification.

**What changes would *not* be risky:** docs, examples, dev-tooling bumps (the 14.0.1–14.0.3 releases demonstrate exactly this low-risk lane: README links, optional chaining refactors, in-place array processing — CHANGELOG.md:30-43).

**Corrosion-vs-evolution verdict on the current trajectory:** the 14.x-line changes (help groups, negative numbers, optional-chaining cleanups) are **evolution**, not corrosion — they extend documented extension points without disturbing the parse core. The one deviation-from-convention worth watching is R6 (signal listeners), a minor hygiene gap, not a design break.
