## 2. Architecture Map

**Module layout** (6 implementation files, 4,214 lines total; plus 1,113-line hand-written typings):

```
index.js (24)          → CJS entry: exports program singleton + create* factories + classes
esm.mjs (16)           → ESM wrapper: re-exports named bindings from CJS core
lib/command.js (2,777) → Command extends EventEmitter — the core: DSL, parser, dispatch, exit, help integration
lib/option.js   (380)  → Option + DualOptions (dual --foo/--no-foo attribution heuristic)
lib/argument.js (150)  → Argument (required/optional/variadic/choices/parseArg)
lib/help.js     (747)  → Help — subclassable formatter (41 methods), color/wrap/groups
lib/error.js    (39)   → CommanderError(exitCode, code, message), InvalidArgumentError
lib/suggestSimilar.js (101) → Damerau–Levenshtein "did you mean" suggestions
typings/index.d.ts (1,113) → hand-maintained public types; esm.d.mts re-exports
```

**The parse pipeline** (verified first-hand; subagent trace; names corrected to v14 reality — there is no `_parseCommandImpl`/`_parseOptionsImpl`):

1. `parse()` / `parseAsync()` (command.js:1090,1119) → `_prepareForParse()` (save-or-restore state, 1127) → `_prepareUserArgs()` (argv slicing by `from: node|user|electron|eval`, 1001) → `_parseCommand()`.
2. `_parseCommand()` (1550) per level: `parseOptions()` (single-pass hand-rolled scanner, 1748) → `_parseOptionsEnv()` (1966) → `_parseOptionsImplied()` (1996) → dispatch ladder: known subcommand → `_dispatchSubcommand()` (recursion, 1352); else leaf checks: help-requested → mandatory options → conflicts → unknown options → `_processArguments()` → `preAction` hooks → action handler → `postAction` hooks (1596-1612). Legacy paths interleave: `command:<name>` events, `*` default command, `command:*` event (1614-1631).
3. `parseOptions()` scanner subtleties (verified): `--` literal handling (1777); negative-number heuristic — regex + "no digit short-option anywhere in the hierarchy" (1757-1766); variadic option continuation (1783); required/optional/boolean consumption (1796-1813); combined short flags `-abc` (1819); `--foo=bar` (1839); unknown-option pivot (1849); positional/pass-through short-circuits (1862-1888).
4. **Value plumbing is event-driven**: `addOption()` registers `option:`/`optionEnv:` listeners at definition time (670-733); the scanner emits; listeners run `handleOptionValue` (preset/parseArg/variadic/negate logic, 692-718) → `setOptionValueWithSource(key, value, source)` (953) → `_optionValues` + `_optionValueSources` (sources: default/env/cli/implied/config/undefined=client).
5. **Exit model**: all errors funnel through `error()` (1940) → `_exit(exitCode, code, message)` (533) → `exitOverride()` callback or `process.exit()`. `CommanderError` is the single error shape (error.js:4-20).
6. **Executable subcommands**: `.command(name, 'description')` marks `_executableHandler`; dispatch spawns `command-subcommand` files via `child_process.spawn` (node for .js/.ts/.tsx/.mjs/.cjs), with symlink resolution, legacy name search, inspector-port incrementing, signal forwarding, and child exit-code propagation (1202-1346).
7. **Help**: `createHelp()` = `new Help()` merged with `configureHelp()` overrides (203); `helpInformation()` → `prepareContext` + `formatHelp` (2450, help.js:443) with term-width wrapping, colors (NO_COLOR/FORCE_COLOR conventions, 2752-2774), help groups (v14 feature).

**Coupling observations (risk-relevant):** Command↔Help are mutually coupled through underscore-privates (6+ private members read by Help — help.js:40-53,82-98,140-153; self-flagged "dubious" help-flag auto-hide at help.js:84; documented side-effect mutating `argument.description` at help.js:139-153). Value-processing logic lives in a closure inside `addOption` — tracing one option value crosses three files (emit → `_collectValue` → listener). The dispatch ladder interleaves modern and three legacy paths.

## 3. Critical Components

**1. The parse engine** (command.js `parseOptions` + `_parseCommand`) — the crown jewel and the highest-risk surface. Every behavior is a documented contract; the test suite locks verbatim error messages and exit codes (command.exitOverride.test.js:120-398), help layout (command.help.test.js:9-25), action binding order (command.action.test.js:5-64), variadic collection (args.variadic.test.js:6-69), and cross-parse state reset (command.parse.test.js:203-336) — C22.

**2. Option/Argument flag parsing** (option.js:328-377 `splitOptionFlags`, argument.js:21-40) — regex-and-bracket based, with explicit "fail noisily" validation for unsupported flags (a v13 tightening, CHANGELOG:83) but several unguarded edges (below).

**3. Value-source machinery** — `_optionValues`/`_optionValueSources` + `DualOptions` attribution heuristic (option.js:268-306) + `_conflictingOption` "educated guess" (command.js:2071-2101). Two heuristic layers exist because dual `--foo/--no-foo` share one value; the class comment itself admits the design is "tricky" (option.js:262-267).

**4. Exit/error machinery** — `error()` funnel + 7 named error helpers with stable codes (`commander.unknownOption`, `commander.excessArguments`, …), `exitOverride()` as the embedding escape hatch. This is what makes commander usable inside other tools (tests, REPLs).

**5. Hand-maintained typings** — 1,113 lines, validated by `skipLibCheck: false` + tsd suite (~290 `expectType`/negative checks in index.test-d.ts:787 lines) + tsc over the JSDoc-checked JS (tsconfig.json:28). One genuine drift found (below).

**6. Executable-subcommand spawner** — the only place commander touches the OS hard: spawn, PATH/extension probing, Windows `process.execPath` path, ENOENT/EACCES diagnostics (1183-1194), signal forwarding (1290-1301).

**7. The test suite itself** — 109 files / ~1,250–1,300 cases is the real safety net that makes the 2,777-line monolith maintainable; harness is inlined (spyOn stdout/stderr/exit, exitOverride+toThrow, real `execFile` against `tests/fixtures/pm*`, mocked spawn EventEmitters).
