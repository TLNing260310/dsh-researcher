**Structural facts that matter**:
- **Command is a God-class**: 66% of the library lives in one file, mixing parsing, process exit, child-process spawning, help rendering, and error formatting. Help/Option/Argument were successfully split out in past majors (v7 era) — the remaining monolith is the accepted price of the fluent single-object API plus two legacy value-storage modes.
- **Parsing is event-driven**: `parseOptions` *emits* `option:<name>` events; listeners registered by `addOption` compute values (`command.js:720–730`). Control flow is indirect — a 2011-era design that is load-bearing for the deprecated public event API (`.on('command:*')`, `.on('--help')`).
- **Two value-storage modes coexist**: `_optionValues` (modern) vs `storeOptionsAsProperties` (legacy) — every value access branches (`command.js:925–961`).
- **State discipline**: `saveStateBeforeParse`/`restoreStateBeforeParse` enable repeated `.parse()` calls (v13 feature).
- **Value provenance tracking**: `_optionValueSources` (default/config/env/cli/implied) powers env precedence, implied values, conflict detection, and help display of defaults.
- **Test estate as behavior lock**: 109 jest files map 1:1 to API areas (`command.*`, `options.*`, `help.*`, `argument.*`, `args.*`, `command.executableSubcommand.*`); plus tsd type tests and an ESM import smoke script.

## (6) Change Impact Analysis

**Context**: this workspace is a *read-only study snapshot* of upstream. Two change scenarios exist: (a) changes *to* this snapshot (none warranted — it is a frozen capture), and (b) changes to code that *consumes* commander (where the impact analysis matters most).

**Scenario 1 — modifying this snapshot (hypothetical fork):**
- **Touching `parseOptions`** (new syntax, new option forms): ripples into `option:<name>` event flow, unknown-option classification, negative-number detection, help usage line, executable-subcommand arg forwarding, and ~20+ test files. Safety net exists but is behavior-based, not golden-output — formatting regressions can slip.
- **Removing a deprecated API** (v15-style cleanup): each removal is *localized* — e.g., `storeOptionsAsProperties` branches in `getOptionValue`/`setOptionValueWithSource`/`opts`/`action` (`command.js:925–961,1902–1917`); legacy `command:*` events in `_parseCommand` (`1608–1620`); `.command('*')` dispatch (`1619–1621`); RegExp param in `_optionEx` (`751–758`); `outputHelp` callback (`2506–2533`). `tests/deprecated.test.js` and `docs/deprecated.md` must move in lockstep. Risk: silent behavior changes for long-tail consumers — exactly why upstream majors ship migration tips.
- **Adding a runtime dependency**: violates the soft zero-dep policy; requires CONTRIBUTING exception; triggers supply-chain review. High bar, by design.
- **Bumping Node engines**: mechanical (package.json + CI matrix + docs), but misaligned with the release-policy timing (next major ≈ Node 20 EOL, April 2026).
- **Typings change**: gated by `tsd` + `tsconfig.ts.json`; `typings/index.test-d.ts` must be extended; CJS/ESM dual entry points (`esm.d.mts`) must stay in sync.

**Scenario 2 — depending on commander from this snapshot:**
- Consumers on 14.x are inside the **maintenance window** (security updates until ~2027-05 per the 12-month policy from 14.0.0's 2025-05-18 release).
- The real decision point is **migration to v15** — already in progress across the ecosystem (dependabot PRs observed). Any new code written against this snapshot should be written to be v15-clean, but v15's exact breaking changes are **unverified here** (fetch provider unavailable) — this is an explicit INVESTIGATE item, not a conclusion.

**Net assessment**: the snapshot's internal architecture is *stable and self-consistent*; no corrosion was found. The dominant change pressure is external (v15, Node EOL, maintenance capacity), not internal.
