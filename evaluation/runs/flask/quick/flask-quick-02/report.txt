## 3. The 3.2.0 context refactor — what actually changed

The merge (issue #5639, PR #5812, commits `c2705ffd`, `6a649690`, `70d04b5a`) collapses `RequestContext` + `AppContext` into one class:

- **One contextvar** (`_cv_app`) backs `current_app`, `g`, `request`, `session` (`globals.py:40-62`); `RequestContext` and `request_ctx` are deprecated module-`__getattr__` aliases with `DeprecationWarning`, removal in 4.0 (`ctx.py:504-515`, `globals.py:65-76`).
- **One combined context per request**: `wsgi_app` pushes an `AppContext` carrying the request; routing, session, teardown all hang off it (`app.py:1562-1582`, `ctx.py:398-480`). `AppContext.__init__(app, *, request=None, session=None)` with `from_environ` factory.
- **Semantic breaks vs 3.1** (verified by diffing `c2705ffd^:src/flask/ctx.py`):
  1. **No context reuse**: 3.1 reused an outer pushed app context during dispatch (shared `g`, implicit-stack bookkeeping). 3.2 always pushes a fresh combined context — so `g` set in an outer `with app.app_context():` is **invisible during a dispatched request**, `appcontext_pushed/popped` fire **per request**, and `teardown_appcontext` runs **per request** even inside an outer app context.
  2. **Lazy session**: opened on first access (3.1 opened at push, before routing). Custom converters can still access `session` during matching (context is set before `match_request`), but custom `open_session` side effects are deferred; `process_response` still touches `ctx.session` unconditionally (`app.py:1403`), so every request still opens a session.
  3. **Signals re-anchored**: `request_started`/`request_tearing_down` now fire from `full_dispatch_request`/`do_teardown_request` (dispatch-bound) rather than context push/pop (`app.py:1001,1430`); inline signal docstrings were removed (`signals.py` is now bare declarations).
- **Subclass compat shim** (`app.py:253-307`): `__init_subclass__` inspects overrides of **12 methods** (`handle_http_exception`, `handle_user_exception`, `handle_exception`, `log_exception`, `dispatch_request`, `full_dispatch_request`, `finalize_request`, `make_default_options_response`, `preprocess_request`, `process_response`, `do_teardown_request`, `do_teardown_appcontext`); old-signature overrides get a `DeprecationWarning` at **class-definition time**, get wrapped by `remove_ctx`, and the base `Flask` class is **globally patched** with `add_ctx`. `wsgi_app` and `create_url_adapter` keep their signatures (the two most-overridden hooks — good call).

## 5. Diagnosis — the important problems, ranked by real-world impact

**P1 — Ecosystem blast radius of the context-reuse semantic change (C4).** The classic patterns `with app.app_context(): ... client.get(...)` (tests) and outer-context `g` as a request-scoped cache silently change meaning: `g` set outside is not visible inside the request, `teardown_appcontext` runs mid-test, and `appcontext_pushed` fires per request. Extensions that store per-request state on `g` in `before_request` are fine; extensions that rely on an *outer* app context being *the same* during dispatch are not. This is a **deliberate, documented simplification** (CHANGES.rst:8-11), not a defect — but it is a hard behavior break with **no warning mechanism**, and it will generate a wave of downstream issues after release. *Severity: high; risk, not bug.*

**P2 — The compat shim is the most delicate new machinery and the least tested (C5, C6, C14, C15).** Four concrete concerns:
- The warn-and-wrap branch (the one real-world old-style subclasses will hit) has **no direct test** in the suite — all 8 `Flask` subclasses in tests use the new signature.
- `inspect.signature(method)` is unguarded (`app.py:280`): a `dispatch_request` wrapped by a signature-mangling decorator raises inside `__init_subclass__`, **crashing the subclass definition at import**.
- The heuristic (param named `ctx` or annotated `AppContext`) misfires on `ctx: "RequestContext"` (the deprecated alias) or differently-named params, producing silent double-wrap behavior.
- Every old-style subclass gets an **import-time** `DeprecationWarning`; under `-W error`/`filterwarnings=error` (Flask's own CI convention) that is a hard import failure for the entire app, not a call-site warning.
- `setattr(Flask, ...)` globally mutates the base class — a cross-subclass side effect that is idempotent-but-fragile (multiple old-style subclasses re-wrap the base).

**P3 — The refactor is incomplete in the documentation surface (C8, C9).** `docs/shell.rst:52,61` shows `app.preprocess_request()` and `app.process_response(app.response_class())` — both now **require `ctx` as first argument** and will raise `TypeError`/`AttributeError` as written. Same page still calls the thing `test_request_context()` creates a `RequestContext` (it now returns `AppContext`). `docs/appcontext.rst:122` has a typo ("requet context"). These are REPL examples, not doctests, so CI never catches them.

**P4 — Minor/positive.** Lazy session loading (C7) is a real but documented change; test-client preservation (C11) is coherent and tested; signals re-anchoring (C10) is documented in `docs/signals.rst:147-150`. No TODO/FIXME markers; `__version__` removal complete (C13); CI matrix is exemplary (C12).

## 6. Challenge (disconfirmation search) — did I get it wrong?

- **Is the refactor corrosion?** No. The reasons the two-context design existed (implicit app-context creation, reuse detection, dual contextvars) were internal complexity with user-visible sharp edges (the `g`-sharing ambiguity itself was a perennial docs/issue topic). The merge *reduces* the abstraction surface, and the `push`-count/`_cv_token` design preserves nesting, streaming (`stream_with_context` re-enters the same ctx), `copy_current_request_context`, debugger preservation, and `with client:` semantics. **Verdict: evolution, not corrosion** — consistent with H2.
- **Would "add more features" be the right diagnosis?** No — feature count is not the bottleneck; compatibility management is.
- **Could the CRLF finding be wrong?** Sampled diffs are unambiguous (`\r\n` on every changed line, identical content otherwise); extrapolation to all 234 files is an inference labeled as such.
- **What would falsify P1's severity?** If upstream 3.2.0 ships with a prominent migration note and the ecosystem absorbs it (as it did the 3.0 sans-io restructure). The semantic break is nonetheless silent in the common test pattern, which is what makes it dangerous.

**Revised hypothesis (H2, current):** coherent, well-engineered evolution with three actionable gaps — untested/delicate compat shim, broken doc examples, and a silent semantics break that needs prominent migration guidance.
