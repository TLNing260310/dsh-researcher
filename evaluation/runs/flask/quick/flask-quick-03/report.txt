## 3. DIAGNOSE — problem chains (problem → severity → evidence → intervention)

### F1 — The compat shim is the most fragile code in the tree, and it is untested
`app.py:253-307`. For each of 12 overridable methods, `__init_subclass__` runs `inspect.signature`, and for old-signature overrides it (a) warns, (b) wraps the subclass method with `remove_ctx`, and (c) **mutates the shared base class**: `setattr(Flask, name, add_ctx(base_method))` — process-global, order-dependent state.

- **Problem chain:** A bug here doesn't fail in Flask's CI — it fails on **first request** in a downstream app. Specific hazard paths:
  1. **Wrapper stacking:** a second old-signature subclass (or a subclass-of-subclass that merely *inherits* a patched wrapper — `method is base_method` is False and the signature check re-warns/re-patches through `__wrapped__`) re-wraps the base: `add_ctx(add_ctx(orig))`. It survives only because `isinstance` checks make the nesting idempotent. Untested correctness-by-accident.
  2. **Heuristic misfires:** a second param named `ctx` but not an `AppContext` → silently treated as new-style (no warning). A `*args`/`**kwargs` second param → spurious warning + wrap. A method that actually needs its argument after a false-positive wrap → **runtime `TypeError` on the first request**, with no warning visible (DeprecationWarning is hidden by default).
  3. **`-W error` inversion:** `add_ctx`/`remove_ctx` are invisible to the user, but the class-creation `DeprecationWarning` becomes an **import-time hard error** in any downstream project running pytest `filterwarnings=error` (Flask's own setting) that imports a library with an old-style subclass.
  4. **Out-of-context `super()` calls** through `add_ctx` raise `RuntimeError: Working outside of application context` (`app_ctx._get_current_object()`) — all current call sites are in-context, but this is a new failure mode for old-style subclasses.
- **Severity:** high — blast radius = the Python web ecosystem; the shim is the *only* thing keeping old-style subclassing libraries alive through 3.x.
- **Evidence:** C4, C5. **Deserves intervention: yes.**

### F2 — The breaking semantic change (context not reused) is under-tested and under-documented
`CHANGES.rst:8-11` documents that an already-pushed app context is no longer reused for a request. Consequences: `g` set in `with app.app_context():` is invisible to a request dispatched inside it; **`appcontext_pushed`/`appcontext_popped` now fire for every request even under a nested app context** (signal-count change for extensions); `teardown_appcontext`/resource scoping (e.g., Flask-SQLAlchemy sessions) shifts.
- **Problem chain:** extensions and apps relying on context reuse get silent behavioral changes after upgrade; no regression test pins the new semantics (C6); no upgrade/migration doc exists (docs were rewritten in the same commit, but there is no 3.2 upgrade guide and `sessions.py`/`test_session_interface.py` still carry pre-merge docs — C7).
- **Severity:** medium-high (expected breaking change, but shipping it without dedicated tests/docs converts it into ecosystem churn and misdiagnosis reports).
- **Evidence:** C3, C6, C7. **Deserves intervention: yes** (tests + doc fixes; scope of the *change itself* is the maintainer's call — it is defensible evolution, see §6).

### F3 — Snapshot hygiene: the entire working tree is CRLF-converted
Every one of 234 tracked files shows `M`; every diff hunk is pure `\r\n` vs `\n`. `.editorconfig` mandates `lf`; `uv.lock` and Python sources are affected; pre-commit's `end-of-file-fixer`/`trailing-whitespace` would rewrite the tree; a commit from this workspace would produce a 100%-file diff and drown any real review. This is a **snapshot artifact, not a repository defect** — but for anyone working from this snapshot it is the first trap, and it can mask real changes in future snapshot diffs.
- **Severity:** high for the snapshot workflow, zero for upstream. **Deserves intervention: yes** (normalize to LF in the workspace/harness; verify `git diff` is clean afterward).

### F4 — Risk concentration in the release path (observation)
3.2.0's substance is one refactor of the hottest code path in the most-used Python web framework, committed directly to main by one maintainer (C8), with the compat layer untested (C5) and the breaking semantics unpinned (C6), and — at snapshot time — no release candidate. The refactor *direction* is justified (single contextvar, less bookkeeping, free-threading friendliness), but the release readiness of the *compat surface* is the bottleneck, not feature work. **Deserves intervention: yes** (test hardening + RC/ecosystem soak before release).

## 4. Tradeoff analysis (relevant axes)

- **Compat shim complexity vs. ecosystem breakage:** the shim trades ~50 lines of adapter machinery for not breaking every old-signature subclass at 3.2.0. Given 3.x's deprecation contract, keeping compat is right — but the *mechanism* (runtime signature inspection + global base-class mutation) is the highest-complexity option; a per-class cached adapter or a documented opt-in would be simpler and testable. Complexity is justified only if it ships tested.
- **Breaking change vs. internal simplicity:** the context merge genuinely simplifies the core (one contextvar, no reuse-detection state machine) — "SQLite doesn't scale" logic applies: for Flask's architecture, the merged context is the simpler design. The cost is a one-time ecosystem migration; the mitigations (tests, upgrade notes, RC soak) are cheap relative to the change's blast radius.
- **CRLF normalization cost:** trivial (re-checkout or renormalize) vs. high cost of *not* doing it (unreadable diffs, pre-commit churn, masked changes).
