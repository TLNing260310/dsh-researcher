# Project Cognition Layer Design Proposal v0.1 — 文档型认知层

> 作者角色:Architecture Research Engineer。任务:研究并设计"仅允许写文档的项目认知层" —— 一个以 `.cognition/` 文档目录为载体的认知协议与维护机制。
> 限制(全部遵守):不修改 researcher runtime / 不新增 agent tool / 不实现 memory 系统 / 只研究文档协议与维护机制。
> 立场:不默认方案成功。§5 专门寻找失败模式,§6 给出与 README/CLAUDE.md 的诚实对比。

---

## 0. 定位(与现有系统的关系)

现有系统已有四个认知构件:`research_checkpoint`(会话内状态机)、`fullExport/importState`(状态转移)、`cognition-state-export.js`(状态投影为机器可读 JSON)、`cognition-diff.js`(状态 vs 代码对账)。它们全部是 **host/evaluator 侧或会话内**的 —— 项目文件系统上没有任何持久认知。

本提案补的是**项目内、人机共读的文档载体**:`.cognition/` 目录。它是:

- **Researcher 输出的落地点**:PCR 的机器可读精华(research_handoff 同族)可以投影进 `.cognition/`(由写权限流程执行,Researcher 本身不写 —— 零写契约不变);
- **Coding Agent 的前置输入**:修改前读取,判断"这是正常重构还是偏离设计";
- **人的文档**:比 README 更结构化、比 ADR 更浓缩、比 CLAUDE.md 更分类。

**它不是 memory 系统**:无自动回灌、无跨会话自动加载、无隐藏状态;它只是 **git 跟踪的普通文档**,任何有写权限的流程(人、CI、授权的 agent)都能维护。本提案只定义**格式协议与维护机制**,不实现任何东西。

## 1. Project Cognition Manifest 最佳格式 —— 七种方案比较

### 1.1 比较矩阵(信息密度 / token 效率)

| 格式 | 结构 | 更新机制 | 机器可读性 | 信息密度 | 失效处理 | 主要缺陷 |
|---|---|---|---|---|---|---|
| **ADR**(每决策一文件) | 强(What/Why/Context/Consequences/Status) | 追加式 | 中 | 低-中(每决策大量叙事) | 状态机(accepted→superseded) | 决策多时碎片化;Why 会过期;读全部成本高 |
| **RFC**(提案文档) | 强(讨论驱动) | 评审流 | 低 | 低(面向讨论,非长期引用) | 状态机 | 是过程文档,不是认知文档;保留价值低 |
| **README architecture** | 弱(散文) | 人工,常过期 | 低 | 中(混在营销/用法中) | 无 | 目标读者是用户不是 agent;结构缺失 |
| **CLAUDE.md** | 弱(指令式清单) | 人工追加 | 低 | 中-高(但指令/事实/约束混杂) | 无显式失效 | 无分类 → 无法局部失效;越长越稀释 |
| **AGENTS.md** | 弱-中 | 人工 | 中 | 中(多 agent 共享,重叠多) | 无 | 与 CLAUDE.md 重复;无生命周期 |
| **Cursor rules** | 中(每规则一文件 + glob 匹配) | 人工 | 高(触发条件化) | 中 | 无 | 面向"规则"不是"认知";无状态/版本 |
| **SWE-agent memory** | 强(事件/主张流,显式状态) | 自动+显式 | 高 | 中 | 显式状态机 | 面向 agent 内部;不是项目文档;无人类可读性 |

### 1.2 结论:最佳格式 = 分层小型文件 + 条目级生命周期

**单一赢家不存在;最优是组合**:

1. **取 ADR 的"决策条目 + 状态机"**,但**砍掉叙事**:每条决策 = 一句话 What + 一句话 Why + 状态 + 证据锚,不写长篇 Context。
2. **取 CLAUDE.md 的信息密度**,但**按认知类别分文件**(core/constraints/decisions/state/drift),让"局部失效"成为可能(只重写 affected 文件,不重写整个认知)。
3. **取 Cursor rules 的"按文件匹配"**,但用于**分类加载**(agent 只读与其任务相关的子文件,而非整目录)。
4. **取 SWE-agent memory 的"主张 + 状态 + 证据"**,但**落成人类可读 markdown**。

**token 效率的三个设计原则**:

- **P1 补集原则**:只存"代码中不可直接恢复的信息"(Why、约束、不变量、风险、意图);不存"代码中可见的信息"(文件布局、API 签名、行号)—— 后者重复且必过期。
- **P2 单文件预算上限**:每个文件 ≤ 特定 token 预算(见 §3),超预算 → 压缩归档(不删除,移入 `.cognition/archive/`)。
- **P3 条目级失效,文件级重写**:条目有 `status`(active/superseded/expired),失效只改条目不改文件整体;文件重写只在漂移确认后。

## 2. 信息分类 —— 什么必须长期保存 / 什么禁止进入

### 2.1 必须长期保存(六类)

| 类别 | 定义 | 为什么必须 | 反例(错误示范) |
|---|---|---|---|
| **项目目标 Mission** | 项目为什么存在;为谁解决什么问题;成功标准 | 所有决策的最终裁判;代码无法自证 | "写一个 CLI 框架"(无 Why) |
| **架构原则 Principles** | 不可违反的结构性约束(分层、依赖方向、零依赖策略等) | 判断"偏离"的基准 | "代码要整洁"(无判定力) |
| **不变量 Invariants** | 在任何修改下必须保持的契约(兼容性、安全边界、数据语义) | 漂移检测的直接对象 | "不要破坏 API"(无具体面) |
| **技术决策 Decisions** | 关键决策 + Why + 被否决的替代 + 状态 | 防止"重新发明轮子"和"无知推翻" | "用了 X 库"(无 Why) |
| **当前状态 State** | 已知偏差、进行中方向、已知技术债、里程碑 | 新 session/新人的起点 | "项目基本完成"(无依据) |
| **已知风险 Risks** | 风险区域(非 bug 预测):脆弱面、耦合点、过期假设 | 修改前的注意力分配 | "可能有 bug"(无锚) |

### 2.2 禁止进入(三类)

| 类别 | 禁止原因 | 处理 |
|---|---|---|
| **临时 debug** | 一次性信息;污染长期认知 | 留在 issue/PR/会话,不进 .cognition/ |
| **已提交代码细节** | 代码本身就是事实源(P1 补集原则);文档重复必过期 | 只留证据锚(file:line/commit),不复制内容 |
| **一次性讨论** | 无长期引用价值;稀释密度 | 留在会议记录/issue,不进 |

### 2.3 判定规则(写入协议,防主观)

> 一条信息是否进入 `.cognition/`,问三个问题:
> 1. **六个月后还需要吗?** 否 → 不进。
> 2. **代码/测试/提交消息能否恢复它?** 能 → 不进(只留锚)。
> 3. **丢失它会造成错误修改吗?** 否 → 不进。
> 三问全过才进入。

## 3. Schema 设计 — `.cognition/` 目录

### 3.1 目录结构

```
.cognition/
├── core.md            # 项目目标 + 架构原则 + 不变量(最稳定)
├── constraints.md     # 硬约束 + do-not-touch 区(次稳定)
├── decisions.md       # 决策日志(追加式,条目生命周期)
├── state.md           # 当前状态 + 已知偏差(最活跃)
├── drift.md           # 漂移检测日志 + 待验证假设(活跃)
├── README.md          # 目录索引 + 维护协议说明(稳定)
└── archive/           # 超预算/过期条目的归档(只增不改)
```

### 3.2 文件职责 / 更新频率 / token 预算

| 文件 | 职责 | 更新频率 | Token 预算 | 超预算动作 |
|---|---|---|---|---|
| `core.md` | Mission(≤3 句)+ Principles(≤7 条)+ Invariants(≤10 条,每条带锚) | 低频(季度级;仅目标/原则变化时) | **≤ 800** | 压缩到 800:合并原则、精简措辞、过期条目移 archive |
| `constraints.md` | 硬约束(资源/兼容/安全/流程)+ do-not-touch 区(带锚) | 低频(约束增减时) | **≤ 600** | 同上 |
| `decisions.md` | 决策条目表(id/date/What/Why/替代/状态),追加式 | 中频(每次关键决策) | **≤ 1200**(条目均 ~40–60 tokens) | 最早 20% 条目移 archive(保留 id 索引) |
| `state.md` | 当前状态:进行中方向、已知偏差、技术债、里程碑 | 高频(每次有状态变化) | **≤ 600** | 过期状态移 archive;只留"现在" |
| `drift.md` | 漂移检测记录:检测到的候选偏离、待验证假设、开发者裁决结果 | 中频(每次检测/裁决) | **≤ 400** | 已裁决条目压缩为一行结论 |
| `README.md` | 目录说明 + 维护协议(三问规则、更新纪律、预算表) | 极低频(协议变化时) | **≤ 300** | — |
| **合计** | | | **≤ 3900 tokens** | 全目录硬上限,防稀释 |

### 3.3 条目格式(统一,机器可解析的子集)

```markdown
## [I-01] 零运行时依赖(原则)
- **类别**: architecture-principle
- **陈述**: 生产代码不得引入运行时依赖;效用代码在树内手写。
- **证据**: package.json(无 dependencies 字段)
- **状态**: active            # active | superseded | expired
- **被推翻条件**: 供应链策略正式变更(issue #NN)
```

- 每条含 `类别 / 陈述 / 证据锚 / 状态 / 被推翻条件`。
- **被推翻条件**字段是关键创新:它使"漂移检测"从"猜测"变成"条件匹配" —— agent 修改时检查是否命中某条目的被推翻条件。

### 3.4 Frontmatter(每文件头部)

```markdown
---
schema: dsh-researcher/cognition-doc/v0.1
file: core
updated_at: 2026-08-23T00:00:00Z
updated_by: <human|researcher-projection|ci>
token_budget: 800
token_usage: 642
---
```

## 4. 架构漂移检测机制

### 4.1 核心问题

> 未来 AI 修改代码时,如何判断"这是正常重构"还是"偏离原始设计目标"?

**正常重构**:实现变了,不变量/原则/目标没变(API 签名换、内部模块移动、性能优化)。
**偏离**:不变量被破坏、原则被违反、目标被无声替换(删 do-not-touch、加运行时依赖、改变核心语义)。

### 4.2 检测规则(机械优先,人工裁决)

| 规则 | 触发条件 | 判定 | 动作 |
|---|---|---|---|
| **R1 不变量违反** | 修改触碰 `constraints.md` do-not-touch 区 / `core.md` invariant 锚定文件 | 偏离(除非该条目的"被推翻条件"已满足) | 停止,询问开发者 |
| **R2 原则违背** | 修改引入新依赖 / 违反依赖方向 / 绕过分层边界 | 偏离候选 | 询问开发者 |
| **R3 决策前提失效** | 修改与 `decisions.md` 中 active 决策的 Why 冲突 | 偏离候选(或决策需 supersede) | 询问开发者 |
| **R4 状态漂移** | 修改后 `state.md` 声称的状态与代码不一致(声明 vs 实现) | 文档过期(非代码偏离) | 更新 state.md,不询问 |
| **R5 证据失效** | 修改使某条目的证据锚失效(blob 变化) | **待验证**(cognition-diff 同族) | 重验证该条目;若陈述仍真 → 更新锚;若陈述失真 → 询问开发者 |

### 4.3 需要询问开发者的条件(预注册清单)

1. **R1 命中 do-not-touch**(无条件询问)。
2. **R2/R3 命中且条目无"被推翻条件"或条件未满足**(询问:是更新认知文档,还是更新代码 — 二选一,agent 不得自行选)。
3. **R5 中陈述失真**(询问:原认知已错(→更新文档),还是代码已偏离(→停止修改))。
4. **新决策需要进入 decisions.md**(询问是否由开发者确认后记录)。
5. **目标级冲突**:修改使项目价值机制(core.md Mission)不再成立(极少见,必询问)。

**不询问**:R4(纯文档过期,自动更新)、R5 中陈述仍真(自动更新锚)、任何"实现细节"级变化(正常重构)。

### 4.4 与 cognition-diff 的关系

- `cognition-diff.js`(已有)提供 **R5 的机械真值**:证据锚 blob 变化 → 待验证条目。
- `.cognition/` 文档是 diff 的**人类可读输出面**:diff 检测 → 条目标"待验证" → 开发者/流程裁决 → 更新或归档。
- **不自动修改任何文档**(零写契约精神延续到文档层:检测自动,修改需授权)。

## 5. 失败模式分析(不默认成功)

### F1. 文档腐化死亡螺旋(最高风险)

**机制**:不更新 → 过期 → agent 不再信任 → 不再读 → 更不更新 → 文档成为装饰。
**证据**:README architecture 的普遍命运;CLAUDE.md 项目大多 6 个月内过期。
**缓解**:token 预算硬上限(小文档易维护)+ R4 自动过期检测 + 更新频率写入协议。**但**如果维护责任悬空(没人被指定写),螺旋必然发生 —— 这是协议解决不了的,需要流程所有权。

### F2. "又一个 CLAUDE.md"(无差异化)

**机制**:如果 .cognition/ 只是"更分类的 CLAUDE.md",且无人机械验证,它**就是** CLAUDE.md,多一层目录而已。
**防线**:`被推翻条件` 字段 + R1–R5 检测规则 + cognition-diff 机械对账 —— 这三者才是与 CLAUDE.md 的本质区别(可验证、可失效、条件化)。**若无这三者,提案失败。**

### F3. token 预算被突破(稀释)

**机制**:信息密度原则(P1)执行不严 → 文档膨胀 → 读成本上升 → agent 跳过 → 腐化。
**防线**:3900 硬上限 + archive 分流。**风险**:archive 无上限积累,索引膨胀 —— 需为 archive 设总预算(如 5000)。

### F4. 双写成本(维护负担)

**机制**:每次修改都要更新文档 → 摩擦 → 被跳过。
**防线**:只要求"修改命中 R1–R3/R5 时"更新;纯实现级修改零文档义务。**风险**:开发者在压力下跳过 → 回到 F1。

### F5. 机械检测的误报(噪声)

**机制**:R5 的 blob 变化 ≠ 认知变化(文件级粒度,行号漂移)。
**防线**:标"待验证"而非"已失效"—— 检测是候选,裁决是人工。**风险**:噪声太多 → 信任流失 → F1。

### F6. 谁拥有写入权?(所有权真空)

**机制**:Researcher 零写契约 → 不能写 .cognition/;若也无其他授权流程 → 无人写。
**防线**:设计为"任何有写权限的流程可维护"(人/CI/授权 agent);Researcher 只通过 handoff 投影(由外部流程落盘)。**风险**:协议定义了格式,但没定义组织所有权 —— 必须在部署时指定。

### F7. 信息重复(与代码注释/文档重复)

**机制**:P1 执行不严 → 重复 → 双源真相 → 冲突。
**防线**:三问规则 + 证据锚代替内容复制。**风险**:主观判定,需要维护纪律。

### 结论(不乐观)

**本提案的成功条件苛刻**:机械检测(R1–R5)+ 预算纪律 + 明确所有权 + 裁决流程,四者缺一不可。**没有机械对账,它就是 CLAUDE.md;没有所有权,它就是死文档。** 失败模式 F1/F2/F6 是结构性风险,协议只能缓解,不能消除。

## 6. 与普通 README / CLAUDE.md 相比是否更有价值?

### 6.1 诚实对比

| 维度 | README | CLAUDE.md | `.cognition/`(本提案) |
|---|---|---|---|
| 信息密度(token 效率) | 低(散文+营销) | 中-高(但混杂) | 高(分类+预算+补集原则) |
| 可验证性 | 无 | 无 | **有**(证据锚 + cognition-diff) |
| 失效处理 | 无 | 无 | **有**(条目状态 + 被推翻条件) |
| 局部更新 | 无(整篇重写) | 无(整篇追加) | **有**(按文件/按条目) |
| 漂移检测 | 无 | 无 | **有**(R1–R5) |
| 维护成本 | 低(但没人维护) | 低(但没人维护) | 中(但维护被检测驱动) |
| 人类可读 | 好 | 好 | 好(比 JSON 状态好) |

### 6.2 判定

- **在"只作为静态文档"时:与 CLAUDE.md 无本质差异**(甚至因多目录而更繁琐)—— 此时不值。
- **在"有机械检测 + 裁决流程 + 所有权"时:有真实增量** —— 增量 = 可验证性(证据锚)+ 可失效性(状态机)+ 条件化检测(被推翻条件)。这三个属性是 CLAUDE.md/README 完全没有的。
- **增量是否值得**:取决于 F1/F6 能否被组织流程解决。**协议本身只提供工具,不提供成功。**

### 6.3 与现有 DSH 认知构件的整合(唯一现实路径)

- `.cognition/` 不是独立方案,而是 **cognition-state(JSON)的人类可读面**:`cognition-state-export.js` 的输出可由授权流程投影为 `.cognition/` 文档(机器可读 ↔ 人类可读双向);`cognition-diff.js` 的 stale 检测直接驱动 R5。
- 这样 `.cognition/` 的价值不依赖"人工持续维护",而依赖**已有的机械对账** —— 这是本提案与"手写 CLAUDE.md"的本质区别。

## 7. 协议要点总结(v0.1)

1. **格式**:`.cognition/` 六文件分层(core/constraints/decisions/state/drift/README)+ archive;总预算 ≤3900 tokens;条目级生命周期(active/superseded/expired)。
2. **信息分类**:六类必须保存(目标/原则/不变量/决策/状态/风险);三类禁止(临时 debug/代码细节/一次性讨论);三问判定规则。
3. **漂移检测**:R1 不变量违反(询问)/ R2 原则违背(询问)/ R3 决策前提失效(询问)/ R4 状态过期(自动更新)/ R5 证据失效(待验证 → 询问);询问条件预注册。
4. **维护机制**:检测自动、修改授权;被推翻条件字段使检测条件化;archive 分流防膨胀。
5. **失败模式**:F1 腐化螺旋 / F2 无差异化 / F6 所有权真空 是结构性风险;成功依赖机械对账 + 所有权 + 裁决流程。
6. **价值判定**:作为独立文档 = 无增量;作为 cognition-state 的人类可读面 + 机械对账的落地面 = 有真实增量。
