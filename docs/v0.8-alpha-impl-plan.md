## #2. File Placement

### 2.1 位置:`evaluation/scoring/`

```
evaluation/scoring/
  cognition-state-export.js   ← 新增(导出器)
  cognition-diff.js           ← 新增(对账器)
  out/                        ← 新增(输出目录,gitignored 可选)
```

**理由**:
1. 与既有评估工具 `score-v11.js`、`build-exp-a-results.js` 同层 —— 它们是 evaluator 侧脚本的先例;
2. `evaluation/scoring/` 不在 eval-lock 的哈希覆盖内(lock 覆盖项:protocol/gt/coverage/snapshot/prompt/preset/config/eval_runtime/runtime_manifest 等;scoring 规则不在锁内 —— 已有先例:score-v11.js 修复未破坏锁);
3. 数据流自然:`session.events.json`(runs/)→ 导出器(scoring/)→ `cognition-state.json` → diff(scoring/)→ 报告(scoring/out/)。

### 2.2 为什么不能放 `evaluation/runtime/`

- `eval-lock.js` 第 56 行:`eval_runtime: sha256Dir('evaluation/runtime')` —— **整个目录哈希被冻结进 v1.1 锁**。
- 在 `evaluation/runtime/` 新增任何文件 → 目录哈希变化 → 未来任何 `--check`(Step-0 锁检查)FAIL → **破坏已冻结的 commander.js.protocol-v1.1.lock**。
- `evaluation/scoring/` 与 `fixtures/blind/` 无此约束(t0-selector.js、mutation-selector.js 已在此目录的新增先例,锁未受影响)。
- 结论:`evaluation/runtime/` 是 lock-covered 禁区,新增工具一律放 `evaluation/scoring/`。

## #3. Cognition State Schema

### 3.1 允许的四类字段(schema `dsh-researcher/cognition-state/v1`)

```jsonc
{
  "schema": "dsh-researcher/cognition-state/v1",
  "run": "#N",
  "project": "commander.js@bf35c5f",
  // ── claims ──
  "claims": [{
    "id": "C07",
    "statement": "...",
    "tier": "C0|C1|C2|C3|C4",
    "verdict": "Known|Likely|Claimed|Unknown|Contradicted",
    "confidence": 0.9,
    "revision": 3,
    // ── evidence anchors(claims 的组成部分)──
    "evidence_anchors": [{
      "ref": "command.js:953-961",          // 原始证据文本
      "file": "lib/command.js",             // 从 ref 解析出的文件(可空)
      "line_span": "953-961",               // 解析出的行区间(可空)
      "blob_sha256": "a3f9c2...",           // 文件当前 blob 的内容哈希(可空 = unverifiable)
      "anchorable": true                    // 是否成功解析(叙述文本可解析出 file:line)
    }]
  }],
  // ── dependencies(逐字段来自现有状态,零增改)──
  "dependencies": {
    "claims": ["C01", "C02", "..."],
    "hypotheses": [{ "id": "H2", "status": "active", "dependsOn": ["C07"], "revision": 1 }],
    "views": [{ "name": "project_model", "dependsOn": ["H1", "H2"] }]
  },
  // ── freshness ──
  "freshness": {
    "generated_at": "ISO-8601",
    "snapshot_commit": "bf35c5f99c20",
    "source_log": "evaluation/runs/commander.js/exp-a/deep/exp-a-deep-01/session.events.json",
    "fold_replayable": true
  }
}
```

### 3.2 禁止字段(明确列出,实现时 schema 校验器拒绝)

- ❌ `user` / `memory` / `preferences` / `profile` —— 无 user memory
- ❌ `plan` / `build_items` / `next_steps` / `recommended_action` —— 无 planning(BUILD 分类属于 PCR,不进状态)
- ❌ `action` / `execute` / `command` / `proposed_diff` —— 无 autonomous action

### 3.3 关键设计决策

- **evidence_anchors 与 claims 的关系**:锚是 claim 的**组成部分**(内嵌数组),不是独立顶层 —— 符合"只能包含 claims/evidence anchors/dependencies/freshness"四类。
- **anchorable 标记**:实证显示 Experiment A 的 evidence 是叙述文本("git log HEAD (bf35c5f...)")。导出器用**保守解析器**(正则提取 `file:line` 模式:文件扩展名 + 冒号 + 行号),**解析失败不丢弃**:`anchorable: false` + `blob_sha256: null`。这类 claim 在 diff 中进 `unverifiable` 桶,单独报告 —— 其占比本身就是"报告缓存化"的实证指标。
- **确定性**:claims/hypotheses/views 的序列化按 id 排序;JSON 输出用固定缩进;同一输入两次导出字节一致(测试 #2 验证)。

## #4. Export Pipeline

### 4.1 数据流

```
session.events.json
  (tool/call research_checkpoint 事件;data.arguments = JSON 字符串 —— 实证已确认)
        │
        ▼
foldCheckpointEvents(events, makeState())     ← require('../researcher/plugins/research-state/index.js').__test
        │   现有纯函数,零修改;内部经 parseCheckpointArgs 处理字符串参数
        ▼
内部 state: { claims: Map, hypotheses: Map, views: Map, dirty: Set }
        │
        ▼
导出器格式化(新逻辑,仅投影):
  1. 对每条 claim 的每个 evidence 文本 → 锚解析器(正则) → evidence_anchors
  2. 对每个 anchorable 锚 → 读快照文件 → sha256(content) → blob_sha256
     (文件读取源 = 冻结快照 D:/AI_work_project/phase-a-snapshots/commander.js/workspace,只读)
  3. 排序、组装 schema v1
        │
        ▼
cognition-state.json(写 evaluation/scoring/out/)
```

### 4.2 关键事实(已实证,写进实现)

1. `data.arguments` 是 **JSON 字符串**(实证:deep-01 的 DISCOVER 调用)—— `parseCheckpointArgs` 已处理,`foldCheckpointEvents` 直接消费。
2. 6 个 Researcher runs 有 checkpoint 事件(21 次调用);6 个基线 runs 无 → 导出器对基线输出**空状态**(claims: [], 仍生成文件,标注 `fold_replayable: true`)—— 这是预期的机制不对称。
3. 快照 workspace 存在且冻结(bf35c5f);指纹计算读它**只读**。

### 4.3 确定性保证

- 同一事件日志折叠两次 → 状态一致(doctor Replay 检查同构);
- 输出 JSON 键序固定、claims 按 id 字典序、anchors 按原始顺序保留;
- `generated_at` 是唯一非确定字段 → 测试 #2 比较时**剥离该字段**。

## #5. Diff Pipeline

### 5.1 数据流

```
cognition-state.json(历史认知,如 T0)
        + 当前 workspace(或注入后的 T1 workspace)
        ▼
cognition-diff.js:
  对每条 claim 的每个 evidence_anchor:
    if !anchorable → unverifiable(不进 stale 判定)
    else:
      current = sha256(当前 workspace 中 file 的内容)
      if current != anchor.blob_sha256 → anchor STALE
      else → anchor FRESH
  聚合:
    claim 的所有 anchorable 锚皆 STALE(或文件缺失) → claim = stale-candidate
    依赖它的 hypotheses/views(经 dependencies) → affected
        ▼
cognition-diff.json:
{
  "stale_claims": ["C07", "..."],
  "affected_hypotheses": ["H2"],
  "affected_views": ["project_model"],
  "unchanged_claims": [...],
  "unverifiable_claims": [...],   // 无有效锚 → 无法对账,单独列出
  "metrics": { "stale_count": n, "unverifiable_count": m, "total": k }
}
```

### 5.2 语义边界(硬性)

- **回答**:"哪些已有认知的证据已变化,因此哪些 claim 是失效候选"。
- **禁止输出**:bug prediction(不输出"这里会坏")、修复建议、严重性分级、claim 内容重评估。diff 的输出只到 `stale-candidate` 与 `affected` 传播为止;**"失效确认"是模型/评估者的后续动作,不是 diff 的输出**。
- **粒度说明**:指纹是文件级内容哈希(sha256 of file content)。文件变化 ≠ 锚定行变化(行号漂移、无关修改) → diff 输出的是**候选**,可能有过报(文件级粒度)。这是已知局限,如实记录在输出 `metrics` 中;行级精化是 v0.9+ 增强,不在本计划。

### 5.3 与 Experiment C+ 的关系

- diff 在 C+ 中作为**机械真值**:注入 mutation 后,机械判定"哪些 T0 claim 应失效" → 与 Researcher 有状态组的实际失效对比 → H2 裁决。diff 不参与任何 run 的输入(不自动加载,禁令 8)。

## #6. Test Plan(四项必须全部通过才验收)

### T1 — 12 archived runs replay

- 输入:12 个 `session.events.json`(exp-a 全部)。
- 断言:导出器全部成功退出;6 个 Researcher runs 输出非空状态(claims > 0);6 个基线 runs 输出空状态且 `fold_replayable: true`;总计 claims 数 = 137(实证基线值)。
- 失败处理:数量不符 → 检查折叠逻辑(事件过滤/参数解析),修导出器,不修插件。

### T2 — deterministic export

- 同一输入运行两次,剥离 `generated_at` 后逐字节一致。
- 断言:严格相等。
- 失败处理:找非确定来源(键序/浮点/缩进),修复,重测。

### T3 — fingerprint reproducibility

- 对快照中同一文件同一路径计算两次 sha256 → 相等;
- 对 anchorable 锚(如 `command.js:953-961` 提取出 `lib/command.js`)→ 指纹非空且可复现;
- 断言:相同输入相同指纹;不同内容不同指纹(修改一行 → 指纹变化)。
- 失败处理:解析器漏锚(anchorable 率异常低)→ 调整正则并记录漏锚分布。

### T4 — synthetic mutation test(关键验收)

- 构造:取 deep-01 的 cognition-state,对快照 workspace 做**一份拷贝**,注入 1 个机械化变更(复用 mutation manifest 的 MUT-01 语义:改 `restoreStateBeforeParse` 的行为,即修改 `lib/command.js` 相应区域);
- 运行 diff(T0 状态 vs 注入后 workspace);
- 断言:
  1. 证据锚指向被修改文件区域的 claim → `stale_claims`(至少 1 条,预期为描述 parse 状态机制的 claim);
  2. 指向未修改文件的 claim → `unchanged_claims`(不被误报);
  3. 输出**不含**任何 bug 预测/建议字段(schema 校验);
  4. 修改无关行(如命令.js 末尾空行)→ 不新增 stale(文件级粒度的已知过报在此可接受,记录 metrics)。
- 失败处理:误报/漏报 → 检查指纹源与锚解析,修工具;仍失败 → 记录为工具局限,降级为"粗粒度对账"并在 C+ 中改用 evaluator 人工判定(H2 实验本身不阻塞)。

### 验收门槛汇总

| 测试 | 通过标准 | 失败动作 |
|---|---|---|
| T1 replay | 12/12 成功,claims=137,基线空状态 | 修导出器 |
| T2 deterministic | 两次输出一致(除 generated_at) | 修导出器 |
| T3 fingerprint | 可复现、变化敏感、anchorable 率记录 | 修解析器 |
| T4 synthetic | stale 命中注入区、unchanged 无误报、零预测字段 | 修工具;若工具失败 → 降级人工判定 |
