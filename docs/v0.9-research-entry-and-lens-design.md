# v0.9 设计：研究入口（Research Entry）与架构透镜库（Lens Library）

> 状态：**提案（PROPOSAL）**，未实现。所有机制主张均标注了证据来源与验证状态。
> 版本基线：仓库 `0.8.0-alpha.10`（发布 tag `v0.8.0-alpha.10`），目标 DSH `0.1.5-rc.3`。
> 约束：不违反 [repositioning-v0.7](./repositioning-v0.7.md) 附录 B 的三条架构红线（不改代码 / 不决定架构方案 / 不预测具体 Bug）。

## 0. 一句话设计

把研究模式从一个**长期驻留的 preset**，改造为一个**按需进入的插件入口**：平时以一行插件安静地待在任意 preset 里，`/research` 时一次性完成「环境切到沙箱级只读 + 组成切成只读认知面 + 选定架构透镜 + 留下可审计的路由清单」，退出时完全可逆。

差异化不在"更会读代码"，而在于**把模型该看哪里这件事变成可审计、可复现、可生长的确定性产物**。

## 1. 已核实的机制约束（设计的事实基础）

这一节是本设计与猜测的分界线。每条都给了来源与验证状态。

### 1.1 权限与沙箱：是**会话日志事件**，不是进程配置

| 事实 | 证据 | 验证 |
| --- | --- | --- |
| `sandbox/mode` 是 durable session event，折叠进 `sandboxMode` projection；`EXECUTION honors the same fold through ctx.sandboxPolicy.resolve()` | `dsh-sandbox-policy/lib/types/session-mode.d.ts` | 已读源码 |
| 唯一写路径是 `setSandboxMode(session, mode)`，**只追加一个事件，无带外状态**；"takes effect on the session's next confined call" | 同上 | 已读源码 |
| 该事件 **log-only，永不进入 model transcript** | 同上（"NOT a surface event… never in the model transcript"） | 已读源码 |
| `sandboxPolicy` 服务本身**只有读方法**（`resolve` / `overrideOf` / `defaultMode` / `workspaceRoot`） | `cordis_inspect Service.sandboxPolicy` | 已查询运行时 |
| 部署预设表：`read-only`（sandbox=read-only, approval=**ask**）、`workspace-write`、`danger-full-access` | `dsh-base/cordis.patch.yml` | 已读源码 |
| `ctx.permissionPresets.set(session, name)` 是官方切换路径；先记 `permission/preset`，再经各 knob 自己的 setter 写入 | `dsh-permission-presets/lib/types/index.d.ts` | 已读源码 |

**结论：沙箱级只读可以在会话中途切换，且切换本身零 transcript 成本。** 用户第 3 点的判断成立。

> **⚠️ P0 修正（实机验证后）**：`SandboxPolicyService` **只有读方法** —— `resolve()` 与 `overrideOf()`；声明里**没有** `setSandboxMode`。`setSandboxMode(session, mode)` 是 `dsh-sandbox-policy` 的**模块级导出函数，不是服务方法**。
> **后果**：`researcher/plugins/tool-restrict/index.js` 里的 `ctx.sandboxPolicy.setSandboxMode(session, 'read-only')` **在 0.1.5-rc.2 上会抛 TypeError**（被它自己的 try/catch 包装成"cannot pin an un-pinned session"）。
> **运行时是唯一已验证可用的写路径**：**`ctx.permissionPresets.set(session, name)`**（`read-only` / `workspace-write` / `danger-full-access`，另加本部署额外注册的 `lt-readonly` / `lt-standard` / `lt-trusted`）。它先记 `permission/preset`，再经各 knob 的 setter 写入。

### 1.2 工具目录（catalog）与沙箱是两个独立平面

| 事实 | 证据 |
| --- | --- |
| `ToolRestriction = { allow?: names; deny?: names }`，语义是"**Global tool names**… removed from **visibility**" | `dsh-tools/lib/types.d.ts:475` |
| 项目自己的注释记录了该限制：`ctx.tools.restrict()` 只认 **global** 名字，因此 preset 平面工具无法被 deny 遮罩 | `researcher/plugins/tool-restrict/index.js:3-11` |
| 工具被隐藏 ≠ 其引导段消失；`tool-fs` 无条件注入 write/edit 引导段，所以必须**同名遮蔽** | `researcher/plugins/tool-restrict/index.js:22-27` |

**结论：** sandbox 负责**安全**，catalog 负责**注意力与 token 节省**。二者必须同时做，且互相不能替代。这正是用户第 3 点的技术表述。

### 1.4 ★ P0 实机验证结果（设计由此改写）

七个探针在一个宿主机进程内实测完成。**这是本设计最硬的一部分：不再是源码推断。**

| # | 结论 | 证据 |
| --- | --- | --- |

| **V2** | **preset 名册**：`standard(ptc,minimal,cordis)` 为 system，`researcher / researcher-deep / researcher-quick` 为 user | 实测输出 |

| **V4** | **对已发布 agent 调 `mount()` 也不会安装 per-agent 部件**：mount 返回 OK、`composedPreset=researcher`，但工具目录仍为空 | 实测 |
| **V5** | ★ **必须在工厂 `setup(agentCtx, agent)` 内 mount**：此时 preset 的行**真的执行了**——`tool-restrict` 的环境预检被触发并**拒绝了**环境不符的 agent（strict 模式 fail-closed） | 实测 |

| **V9** | 一次性 agent 的创建/销毁**对源会话零影响**（`sourceEnvAfter` 与之前完全一致，agents 列表回到原状） | 实测 |

**由 V3+V4+V5 得出的架构结论（改写 §4.1）**：

> **`/research` 不能用"原地 recompose 会话"实现。** 无论 `recompose` 还是对已发布 agent 调 `mount`，得到的只是一个 scope 重绑——preset 的 per-agent 安装（永拒桩、prompt 遮蔽、环境预检）**都不会运行**，而正是这些构成了只读契约。
> **唯一正确的构造是：在 agent 创建时、`setup` 内部 mount。** 这要求为研究模式**新建一个 agent**，而不是复用当前 agent。
> **上下文延续用 fork 解决**：`sessions.fork()` 已验证可用，且保留 cwd 与全部历史（V8）。所以 `/research` 的形态是：
>
> ```
> 当前编码会话（可写）
>   └─ /research <task>
>        ├─ ① sessions.fork(当前会话)         → 新会话，携带全部历史与 cwd
>        ├─ ② agents.create({ sessionId, meta.cwd, setup })
>        │       └─ setup 内依次：
>        │            · permissionPresets.set(session, 'read-only')
>        │            · approval.setPolicy(agent, 'never')
>        │            · await agentPresets.mount(agentCtx, '<research-preset>')
>        └─ ③ 新 agent 在只读环境中开始研究
> ```
> 这三步**已端到端实测通过**（V7）。

**未验证（1 项，留待真实会话）**：`tools.get(name, scope)` / `tools.schemas(scope)` 对 preset 平面工具的**名字级**可见性，本探针读不到（在不同 context 下解析）。**故"catalog 里确实少了 write/edit、省下多少 schema 字节"这一条尚未取得数字** —— 需要一次真实研究会话来测量（A4）。

## 2. 设计定位：这是一个 **DSH 插件项目**，不是独立应用

按用户第 1 点的定性，本项目是 DSH 插件。这不只是归类问题，它决定了三件事：

1. **能力边界由 DSH 的 service 契约决定，不由我们发明。** 我们只组合 `commands` / `agentPresets` / `sandboxPolicy` / `approval` / `tools` / `systemPrompt` / `skills` / `goals` 这些既有 seam。
2. **分发路径是 preset 目录 + 安装器**，因此 4.4 的版本漂移是**分发缺陷**而不是功能缺陷。
3. **它必须能在别人的 DSH 上装得上**。任何依赖本机特殊状态的实现都是不可接受的。

---

## 3. 设计原则（非协商项）

- **P1 只读由环境保证，不由纪律保证。** 沙箱级 `read-only` + `approval never` 是底线；工具层桩只是补充。
- **P2 注意力节省来自"不出现"，不来自"被禁止"。** 不进入 catalog 的工具、不注入的引导段，才是真正省下输出与注意力预算的部分。
- **P3 选择必须可见。** 透镜的选取与跳过都要写进产物；不可审计的路由等于没有路由。
- **P4 透镜写成肯定式检查问题。** 依据：LLM 对否定系统性不敏感（arXiv:2306.08189）；禁令不可依赖，约束要下沉到确定性验证器。
- **P5 外部化优先于自省。** 依据：无外部反馈时 LLM 无法可靠自我纠正（arXiv:2310.01798）。所以透镜必须绑定证据，`CLEAR` 必须写出反证条件。
- **P6 增量不破坏既有约束。** 不改 `tool-restrict` 的零写契约、不改 `research-doctor` 的证书语义、不改 `research-state` 的 reducer。

## 4. 架构

### 4.1 四步入口（已按 P0 实测结果改写）

**原方案（原地 recompose）已被证伪**（V3/V4/V5）：对已发布 agent 做 `recompose` 或 `mount` 只重绑 scope，preset 的 per-agent 安装不会运行，只读契约不会建立。**必须新建 agent，并在 `setup` 内完成装配。**

```
普通编码会话（可写，default preset = minimal 或 standard）
  └─ 插件行 research-entry        ← 唯一常驻物：只注册 /research，不做别的事
        │
        │  用户输入 /research <task>
        ▼
  ┌──────────────────────────────────────────────────────────────┐
  │ ①  sessions.fork(当前会话)                                   │
  │      → 新会话，携带全部历史 + cwd + isSeeded（上下文不丢）    │
  │                                                              │
  │ ②  agents.create({ sessionId: fork.id,                       │
  │                    meta.cwd: fork.header.cwd,                │
  │                    seed: fork.snapshotEvents(),              │
  │                    setup })                                  │
  │                                                              │
  │      setup(agentCtx, agent) 内，严格按序：                    │
  │        (a) permissionPresets.set(agent.session, 'read-only') │
  │              → 追加 sandbox/mode 事件，零 transcript 成本     │
  │        (b) approval.setPolicy(agent, 'never')                │
  │              → 无升级路径                                     │
  │        (c) await agentPresets.mount(agentCtx, '<research>')   │
  │              → per-agent 安装在此刻真正执行（守卫会自检环境）  │
  │                                                              │
  │ ③  lens-router 扫信号 → 产出 Route Manifest → inject          │
  └──────────────────────────────────────────────────────────────┘
        │
        ▼
  新建的只读研究 agent：沙箱 read-only + approval never + 只读 catalog
  透镜集作为模型可见上下文注入，研究 persona 接管
  原编码会话原封不动保留（V9 实测：零影响）
```

**顺序不可调换**：`tool-restrict` 的环境预检在 mount 时执行，它要求会话已经是 `read-only` + `never`。实测中先 mount 后切权限会 fail-closed 拒绝创建（V5）；按 (a)(b)(c) 顺序则**创建成功**（V7）。

**出口**：关掉研究 agent，回到原编码会话——原会话从未被改动，所以"退出"是零成本的。因为是新建 agent 而非改造，**不存在需要回滚的中间态**。

**为什么不做成"另一个模式实例"**：模式实例需要主循环支持，我们没有那个 seam；而"新建 agent + setup 内装配"组合出的效果等价，且**完全走既有机制**（`fork` / `create` / `permissionPresets.set` / `mount` 全部是已发布 API）。

**代价与诚实说明**：这个形态要求用户接受"研究在一个新会话里进行"。这是**机制强制的**，不是设计偏好——`/research` 无法把一个已发布的编码 agent 变成只读 agent，因为只读契约的安装窗口只在创建期存在。

**V7 实测的完整编排输出**（供实现时对照）：

```
permissionPresets=present, names=read-only/workspace-write/danger-full-access/lt-readonly/lt-standard/lt-trusted
sourceEnv: override=danger-full-access resolved=danger-full-access approval=never
1. step-blocker installed
2. env(before): override=undefined resolved=workspace-write approval=undefined
3. permissionPresets.set(session, read-only) OK
4. approval.setPolicy(agent, never) OK
5. env(after): override=read-only resolved=read-only approval=never
6. MOUNTED id=researcher
CREATED agent=...
env(final): override=read-only resolved=read-only approval=never
sourceStillLive=true   sourceEnvAfter: override=danger-full-access ... (与之前完全一致)
```

注意第 2 行：新建会话的**初始**环境是 `resolved=workspace-write`（来自 `permission.defaultPreset`），且 `approval=undefined`。所以**第 3、4 步必须显式执行**，不能指望 preset 自己收紧——`tool-restrict` 的 pin 分支只在**两个 override 都为 undefined** 时才触发，而新建会话的 sandbox override 由 `permission.defaultPreset` 填入，pin 分支不会命中，它会改为**校验并拒绝**。

### 4.2 保证强度分三级，并如实上报（解决"工具层改沙箱级"）

| 级别 | 条件 | 报告 |
| --- | --- | --- |
| **SANDBOX** | `ctx.sandboxPolicy.resolve({session}).mode === 'read-only'` 且 `ctx.approval.overrideOf(session) === 'never'` | `GUARANTEE: SANDBOX` |
| **CATALOG** | 沙箱为 read-only，但 approval 非 never | `GUARANTEE: CATALOG (no escalation guarantee)` |
| **DEGRADED** | 沙箱非 read-only | `GUARANTEE: DEGRADED — 该会话无法建立只读保证；拒绝以研究模式运行` |

沿用项目既有诚实性原则（`researcher/README.md:69`：不同强度不得混称），并把**保证强度本身作为报告的第 0 节**——这一点是外部项目做不到的。

**关于 `approval: never` 的一个必须写清的副作用**：它同时封掉了"合法升级"。因此 `/research` 必须**只由人类命令入口触发**，且进入前要明确告知"研究模式期间不会为任何写入征求许可"。这是产品语义，不是漏洞。

### 4.3 组件清单

| 组件 | 类型 | 位置 | 职责 |
| --- | --- | --- | --- |
| `research-entry` | 插件 | `researcher/plugins/research-entry/index.js` | 注册 `/research`；执行 §4.1 四步；上报保证强度；写入进入意图事件 |

**分叉已由 P0 解决**：不需要新增"不依赖 `agent/created` 的极简 preset"，因为实测证明**在 `setup` 内挂载现有 `researcher` preset 时，per-agent 安装会正常执行**（V5 的守卫触发即为证据）。**复用现有 preset**，不再引入第四个 preset 目录。

**`research-entry` 的两条硬约束（实现时必须遵守）**：

1. **`setup` 内的顺序固定为 `permissionPresets.set` → `approval.setPolicy` → `mount`**，因为 `tool-restrict` 的环境预检在 mount 时执行（V5/V7）。
2. **只用 `ctx.permissionPresets.set()` 写权限**。**不要**调用 `ctx.sandboxPolicy.setSandboxMode(...)` —— 该方法在服务上不存在（§1.1 的 P0 修正），会抛 TypeError。

| 文件 | 行 | 现状 |
| --- | --- | --- |
| `researcher/plugins/tool-restrict/index.js` | **248** | `ctx.sandboxPolicy.setSandboxMode(session, 'read-only')` → 会抛 TypeError，被本函数 try/catch 吞成 "cannot pin an un-pinned session" |
| `evaluation/presets/researcher-quick/plugins/tool-restrict/index.js` | **166** | 同上 |

### 4.4 数据流与产物

```
signal scan ──► Route Manifest ──► inject ──► 研究 persona
（确定性）      （可审计产物）     （当前步）
                     │
                     └──► 与 research-state 的 claim ledger 绑定：
                          每条发现标注归属透镜；每条选中透镜必须有裁决
                          HIT / CLEAR / UNKNOWN
```

Route Manifest 是所有权的载体，字段固定：

```json
{
  "schema": "dsh-researcher/route-manifest/v1",
  "guarantee": "SANDBOX | CATALOG | DEGRADED",
  "signals": [
    { "id": "dep:openai", "kind": "dependency", "evidence": "package.json:41", "weight": 2 },
    { "id": "path:migrations/", "kind": "structure", "evidence": "migrations/ (12 files)", "weight": 2 }
  ],
  "selected": [
    { "lens": "A-L2", "score": 5, "why": ["dep:openai", "path:providers/"] }
  ],
  "skipped": [
    { "lens": "L2.1", "why": "no migrations directory, no ORM model files" }
  ],
  "unassessable": [
    { "lens": "L5.2", "why": "evidence anchor 'prometheus/rules/*.yml' absent" }
  ]
}
```

`skipped` 与 `unassessable` 是**必需字段**，不是可选项。这是 P3 的落地方式，也是透镜库可度量的前提。

## 5. 透镜库（Lens Library）

### 5.1 条目的六字段模式

```yaml
lens: A-L2
name: 能力矩阵 vs 最大公约数 (Capability Matrix vs LCD)
domain: multi-provider-adaptation
trigger: 仓库中出现 ≥2 个 model provider，或自建 LLMClient/provider/adapter 抽象
questions:                          # 必须能用 path:line 回答；必须是肯定式

## 6. 知识库：如何搞到优秀的作者经验（用户第 2 问）

这是当前最大的空白，也是最难自动化的部分。先把事实说清楚：

**现状证据**：全仓 grep（`lens` / `透镜` / `heuristic` / `检查清单` / `playbook` / `痛点` / `taxonomy` / `知识库`）后，**不存在任何可复用的领域知识资产**。现有的注意力引导全部是"单一 persona prompt + 2 个 SKILL.md"，总量约 23 KB 线性散文，不可检索、不可增长、不可路由。

### 6.1 经验知识的三种形态，采集方式完全不同

| 形态 | 例子 | 采集方式 | 可持续性 |
| --- | --- | --- | --- |
| **规范型**（authoritative spec） | MCP 规范各修订版、RFC 9110、PostgreSQL 隔离级别文档、OWASP ASVS、K8s 探针文档 | 直接引用 + 版本钉扎；规范改动即触发透镜复审 | 高（有明确修订与 changelog） |
| **模式型**（distilled patterns） | Release It! 稳定性模式、Azure Cloud Design Patterns / Antipatterns、microservices.io 模式语言、SEI tactics、AWS Well-Architected 反模式清单 | 一模式一透镜；反模式清单尤其适合（负面清单比正面原则更可检查） | 高（书/目录稳定） |
| **经验型**（practitioner experience） | 工程博客复盘、事故报告、QCon/InfoQ 演讲、"我们试了 N 个月"报告 | **不能自动采集**；必须人工蒸馏 + 署名 + 溯源 | 低（会过期、有版权约束） |

**关键判断（已由调研修正）：真正的稀缺不是"经验分享没有"，而是"经验分享没有被蒸馏成可检查的形式"，而且公开性本身就是瓶颈。**

证据：
- Dan Luu 在其 post-mortems 索引 README 中写道：*"most of the interesting post-mortems I know about are locked inside confidential pages at Google and Microsoft"* → **是公开性稀缺，不是经验稀缺**。
- 一位实践者人工评审 **800+ 家公司工程博客，仅约 157 篇（~20%）达标**；并发现**博客质量跟随个人而非公司**，且**发文频率与质量几乎不相关**（部分最高信号博客每年只发 3–4 篇）。
- 结论：语料充足但**不可导航**，且**公司 logo 与发文频率是反向指标**。→ **发现层应按 byline（作者）建模，而不是按公司建模。** 这一条直接改变 P4 的实现：透镜的 `provenance` 应记**作者**，来源订阅清单应跟人而非跟组织。
- 中文侧有一个干净的负结果：**不存在**中文版 Dan Luu post-mortems 集合，也**不存在** k8s.af 的中文等价物。公开故障复盘在中文语境里是「半公开 genre」——内部强制、对外高度选择性，且深度技术复盘常以"混沌工程/压测/演练/变更管控"经验分享包装，而非以事故命名。

### 6.2 采集管线的设计要点

**★ 决定性事实（同时锁死架构与许可）：`aipref` 的 `search` 类别明确排除 summaries。**

IETF `aipref` WG（Active，`draft-ietf-aipref-vocab-08`，2026-09-13）把偏好词表定为三类：`train-ai` / `ai-use` / `search`，而 **`search` 的语义不含摘要**。这意味着——**"我们只是做索引"这句话不覆盖 LLM 摘要**；蒸馏层很可能需要 `ai-use` / `ai-input` 许可。

**这把"分析留在用户侧"从一个审慎选择升级为架构必需项。** 结合 RSL 1.0（Recommendation，2025-12-10，编辑方含 Schema.org、Yahoo、Automattic、O'Reilly）与 Cloudflare Content Signals，冲突规则两边一致：**最严格者胜**（RSL：「the prohibition MUST take precedence」；aipref §5.1：任一偏好声明 disallowed 即 disallowed）。

**因此管线切成三层，这不是策略偏好而是唯一能在许可变化时仍然正确的结构**——因为 repo 里从来不含任何需要重新清权的东西：

| 层 | 位置 | 内容 | 法律基础 | 可再分发 |
| --- | --- | --- | --- | --- |
| **T0 随附** | OSS repo + release artifact | lens ID、域、痛点/失败模式/替代设计（**我们自己的 paraphrase**）、源 URL、标题、作者、日期、SPDX id + `license_class`、内容 hash、ETag/Last-Modified、检索时间戳、策略检查记录、人工评审记录 | 事实 + 我们自己的版权 | ✅ |
| **T1 构建期** | `.cache/`（gitignored），用户机器 | 抓取正文、抽取正文、embedding | **用户自己的阅读** | ❌ 绝不 commit |
| **T2 运行时** | 用户机器 / 其自有向量库 | 实时重抓、新鲜 embedding、按需摘要 | 用户在各站点自身 ToS 下的行为 | ❌ |

必须实现 `--offline`（仅 T0，仍完全可用）与 `--no-fetch` 两个模式。

**五级摄取判定（(d)(e) 是最容易被忽略的）**：

| 级别 | 存什么 | 可 ship？ |
| --- | --- | --- |
| (a) 链接 + metadata | URL/标题/作者/日期/hash/许可 | ✅ **这就是核心** |
| (b) 短引用 + 署名 | 逐字 span，**≤25 词、每源 ≤1–2 处**，进机读 quote ledger | ⚠️ 有条件 |
| (c) 大量摘录 / 全文 | — | ❌ **完全不入库** |
| (d) 衍生蒸馏 | 六字段 lens | ⚠️ **只允许我们自己的 paraphrase**，绝不允许机器逐字输出；**"换了 schema"不构成豁免** |
| (e) 嵌入向量 + chunk | — | ❌ **绝不随 repo 分发**（向量派生自表达，随行 chunk 文本则是无可争议的复制） |

**许可分域的一个前置事实**：**代码许可不覆盖 README/docs 里的散文。** CC 官方明确 "CC licenses may be used for software documentation" 且不建议用于软件本身；choosealicense.com 把"非软件项目"做成独立分支；SPDX 把内容许可（CC-BY-4.0 等）与软件许可**分列为一等标识符**。→ 所以仓库必须显式切分 `LICENSE-CODE` / `LICENSE-DOCS` / `NOTICE`，**不得只写一个 `"license": "MIT"` 就假定覆盖 `docs/*.md`**。

**其他治理要点**：

1. **只蒸馏，不搬运。** 版权上安全的分界是：**链接 + 事实 + 我们自己的检查问题**安全；**大段引用原文**不安全。
2. **溯源与新鲜度是一等字段，且 `content_hash` 必须带 `hash_scope` 与 `extractor`**（如 `readability_main_text_v2_utf8_nfc_ws_collapsed`）——**否则每次重新抽取看起来都像"变了"**。这是回答"源是否变化"唯一可复现的方式。
3. **定位符存 W3C 式 text-quote（prefix/exact/suffix）并同时存 char offsets**：前者在重新抽取后仍存活，后者不会。
4. **`prov:wasGeneratedBy` 记 `prompt_sha256` + `config_sha256`**：蒸馏可复现；若某模型日后被发现泄漏，能定位所有受影响 lens。
5. **`access.*` 让伦理姿态可审计**——记录**何时**检查过 robots.txt / aipref / RSL。权利人找上门时这是证据。
6. **RSL 的强制 `max-age` 再验证（默认 30 天）可直接复用为 freshness 引擎**，配合 `Last-Modified` / `ETag` / sitemap `<lastmod>`。
7. **人工评审是必要环节，不是瓶颈。** 见 §6.3。
8. **发现渠道优先于抓取**：规范 changelog / RSS / 厂商 incident 报告有稳定更新节奏，比零散搜索可靠。
9. **维护节奏与废弃策略**：规范型 6 个月、模式型 12 个月、经验型 12 个月复审；过期未复审者在路由时降权并标注 `STALE`，**弃用绝不静默删除**（tombstone 保持可引用性）。

### 6.3 两遍 span-anchored 蒸馏（同时解决许可、可验证性与幻觉）

**硬承诺：每一条 claim 必须追溯到逐字源 span，否则不分发。**

- **Pass 1 — 只抽 span，不生成。** LLM 处于仅抽取模式："返回输入中陈述痛点、失败模式或替代设计的最小逐字句子。逐字复制。若无则返回空列表。"输出 `[{text, char_offsets}]`。**机械验证** `source_text[offsets] == span`——**不做模糊匹配、不做归一化**。验证失败即丢弃，不修补。
- **Pass 2 — 只从 span 抽象。** 模型**只看已通过验证的 span，永不见全文**，并为每条断言输出 `claim_id` 指向支撑 span。**这使"表达转移"在结构上变难：模型根本看不到作者在 span 之外的散文节奏。**

**Guardrails（按重要性）**：① span 字节精确存在性；② **换模型做 entailment check**（no/unclear 一律拒绝，避免相关性错误）；③ 数字保真检查（claim 中每个数字必须出现在支撑 span 中且值与单位一致——这捕捉最常见也最有害的一类幻觉）；④ 引用预算（每源 ≤2 处、≤约 25 词，全库引用词比 < 5%）；⑤ no-substitution 检查；⑥ strict JSON Schema；⑦ 确定性包络（`temperature=0`、固定模型版本与 prompt hash）；⑧ **自由弃权**——"证据不足"是一等答案，**2 条锚定良好的 claim 优于 8 条摇摇欲坠的**。

> ⛔ **必须在 CONTRIBUTING.md 中显式禁止的 anti-pattern：「summarize this article」。** 该指令最大化表达转移，正是法律分析警告的行为。

**人工评审的降疲劳机制（关键：审 diff，不审文档）**：把**源 span 与 claim 并排**给评审者，**绝不把整篇文章与整个 lens 并排**——审 span 约 30 秒，审文章 10 分钟，**疲劳正是在那里杀死质量**。按风险分队列（A 机器抽取的 span / B 合成 claim / C 许可例外）；按源批处理；队列硬上限；二人规则用于携带逐字引用或具名归因于特定公司的 lens；抽审 5% 并以**分歧率作为质量 KPI**。

### 6.4 CI 中唯一必须做对的一条规则

> **CI 必须能够因为"一个 PR 提交了第三方文本"而 fail。**

其余都是卫生，**这一条是法律控制**。阻断项：strict JSON Schema、provenance 完整性（每条 claim 至少一个带 `quote_sha256` 的 support；每个 source 有 `retrieval`/`access`/`licensing`）、引用预算与许可门（**拒绝来自 `noderivatives` / `unknown` 的任何引用或蒸馏散文**）、模型/prompt provenance、SPDX id 校验、`gitleaks`。咨询项：链接检查（`lychee`）、`vale` 散文 lint、蒸馏 eval（`promptfoo`）。

`license_class` 枚举：`permissive | attribution | sharealike | noncommercial | noderivatives | all_rights_reserved | public_domain | unknown`，**`unknown` 一律按 `all_rights_reserved` 处理**。

### 6.5 命名失败模式必须有 primary source（否则不入库）

透镜的 `failure_modes` 字段**不能写没有出处的"具名模式"**。已核实的权威对照：

| 模式 | **命名的 primary source** |
| --- | --- |
| **Metastable failure** | Bronson, Aghayev, Charapko, Zhu, HotOS '21, pp. 221–227, DOI `10.1145/3458336.3465286` |
| **Gray failure**（差异化可观测性） | Huang et al., HotOS '17, DOI `10.1145/3102980.3103005` |
| **Retry storm / death spiral / persistent congestion / overload / cascading failure** | 这些**是同一机制的不同实践者叫法**，直到 Bronson et al. 2021 才统一 |
| **Coordinated omission**（测量失败模式） | Gil Tene, *How NOT to Measure Latency*, QCon SF 2012；Schroeder/Wierman/Harchol-Balter, NSDI 2006 |
| **复杂系统失败模式 18 条** | Cook, *How Complex Systems Fail*（© 1998–2000）。其中 #18「**Failure free operations require experience with failure**」是"为何重视一手经验"的**机制性论证**，比稀缺性论证更有力 |
| **构建系统注入式供应链后门** | CVE-2024-3094；canonical writeup 是 `openwall.com/lists/oss-security/2024/03/29/4`（xz 5.6.0/5.6.1） |

> ⛔ **不得作为具名模式使用的"民间传说"**：`thundering herd`、`cache stampede`、`correlated failure`、`backpressure collapse`、`certificate expiry`、`bimodal performance`——**均未找到 primary source**，只能作为现象描述，不得作为命名模式入库。

**模式复合优于单一根因（这是透镜的写法论据）**：Slack 2021-01-04 的复盘（Laura Nolan）一篇之内含**六种**具名模式：网络降级 → 丢包 → 线程池饱和 → **按代理指标（CPU）的 autoscaler 缩容** → provision-service 资源耗尽（ulimit + AWS 配额）→ ASG 上限 → 可观测性丧失。**没有一种罕见。** → **透镜必须描述因果链，不能描述单一根因**；这也是为什么 §5.1 的 `failure_modes` 是复数。

### 6.6 这个项目的知识贡献边界（诚实的负结果）

调研得到若干**干净的负结果**，它们既是本项目的定位依据，也是必须写进 KB README 的可反驳声明：

1. **没有任何关于复盘"消费"的研究**——生产被测量，价值被规范断言，但**没有阅读率、复用率、action item 闭环率的研究**。"write-only memory" 是专家观察，**不是测量**。
2. **没有任何组织公布 internal:public 复盘比率。**
3. **★ 没有架构评审 / ATAM 的效应量实证研究**——只有 SEI 的描述性材料，**未找到任何受控或准实验研究把"评审者经验"与"静态分析"对架构评审价值的贡献分离开**。
4. **没有公开的复盘语料数据集**（arXiv 零结果；incident.io / FireHydrant / Kaggle / HuggingFace 均无）。
5. **SE 中不存在"知识蒸馏瓶颈"名义下的研究**；最接近的是 grey literature / multivocal literature review 方法论——**这个领域正在发明工具来弥补蒸馏缺口，这本身就是支持本判断的证据**。

→ **本项目的知识贡献不是"发现了没人知道的失败模式"，而是"把散落且无人消费的经验，蒸馏成可路由、可裁决、可追溯的检查视角"。** 这个定位诚实、可辩护，且不与任何既有工作冲突。

**问题陈述（可直接引用的一手材料）**：2017 年 SNAFUcatchers / STELLA 工作坊（Etsy、IBM、IEX、俄亥俄州立大学，约 20 位资深实践者）在报告 `snafucatchers.github.io` 中写道：

> "Some firms have libraries of postmortems but there appear to be **few people who have library cards** and even fewer prone to check out a volume and peruse it. ### 7.6 `/research` 的最终形态：会话内为主，派生为可选（owner 决定，已实现）

**原实现只有派生模式**（fork 会话 + 新建 agent）。owner 指出这会造成**会话切换**，而他要的是"会话中途可用、由主 agent 继续执行"。因此改写为双模式：

| 模式 | 命令 | 行为 | 只读强度 | 研究 persona |
| --- | --- | --- | --- | --- |
| **会话内（默认）** | `/research <任务>` | **当前会话**切只读 + 装工具层守卫 + 注入 Route Manifest，**主 agent 继续执行** | 沙箱只读 + 工具层拒绝 shell/写工具 | 无 |
| **派生（可选）** | `/research --session <任务>` | fork 会话 + 新建 agent + setup 内 mount preset | 沙箱只读 + 审批 never + 全部 per-agent 安装 | 有，含 Runtime Certificate |

**为什么会话内模式必须再加一层工具层守卫**：`permissionPresets` 只约束**文件系统**能力。它拦不住 `pwsh -c "Set-Content ..."`——shell 里的写穿过 fs 沙箱。只切权限而不加工具层守卫，会得到"看起来严格、实际可绕过"的治理，正是本项目最反对的东西。守卫拒绝 `write` / `edit` / `bash` / `pwsh` / `shell` / `terminal*` / `persistent*` / `subagent*` / `workflow` / `ralph` / `run_code`。

**如实记录的代价**：会话内模式**没有研究 persona**，也没有 `research_doctor` / `research_checkpoint`。原因是 DSH 只在 agent **创建期**的 setup 内应用 preset 的 per-agent 安装（§1.4 的 V3/V4/V5 实测）。所以**只读契约可以在会话中途建立，研究认知面不能**。需要完整认证形态时用 `--session`。

**退出**：`/research off` 恢复进入前的 permission preset 并释放工具守卫。进入前会记录 `permissionPresets.current(session)`；若进入前是 `custom` 组合则不自动回退，如实告知用户用 `/permission` 选择。

**本轮实测确认的两件事**：
- 跨 preset 引用插件**只能用相对路径**：`'../researcher/plugins/research-entry/index.js'` 可解析；`'~/.dsh/...'` **不解析**（`~` 不被展开），报文为 "names a plugin that cannot be resolved"。
- **注意**：会话内真实生效需要宿主重启。开发期在运行进程内 `require()` 过该插件后，旧模块会被缓存，挂载审计会报旧的进程级服务名。

### 7.7 需要外部专业判断的一项（不可自行决定）

**蒸馏 lens 是否构成衍生作品，无亮线答案。** 两种竞争框架：(i) 输出是事实提取的转化性新作 → 低风险；(ii) 紧密改写构成衍生作品或侵权改编，**"换了 schema"不豁免——如果表达跟着走了**。风险随三点急升：保留了多少独特措辞、是否替代原文、是 per-lens 还是 per-article。

→ **建议就"蒸馏模式"请律师审一次，并把结论编码为 CI 规则**。这是本项目性价比最高的一笔法律支出。其余可自行降险的措施（quote ledger、保留策略检查审计日志、公开删除联系与流程、`--offline`/`--no-fetch`）不依赖该结论即可先做。

## 附录 A — 经验采集：已核实的可达路径与治理结论

> 状态：调研完成（四条研究流：可达性、英文源、中文源、资产与许可、法律与治理、稀缺性验证）。正文 §6.2–6.6 已吸收其架构与治理结论，本附录保留**操作性事实**（可达性、许可分级、资产优先级、量化实证）。

### A.1 可达性实测结果（决定管线怎么搭）

**不可达（会直接卡住采集）**：`github.com` 与 `raw.githubusercontent.com`（DNS 解析到非公网 IP）、`web.archive.org` / `archive.org`（**没有 Wayback 兜底，link-rot 只能靠本地缓存或引用日期**）、`martinfowler.com`、`dl.acm.org`、`queue.acm.org`、`sre.google`、`medium.com`、`substack.com`、`v2ex.com`、`infoq.cn`、`sourcegraph.com`。

**可达，且是 GitHub 内容的替代入口（对"分发靠 GitHub"的本项目尤其重要）**：

| 路径 | 形式 | 用途 |
| --- | --- | --- |
| `cdn.jsdelivr.net` | `https://cdn.jsdelivr.net/gh/<owner>/<repo>@<ref>/<path>` | **主替代**：把任意 GitHub 文件读成纯文本，已验证可取回完整 markdown |
| `codeberg.org` | Forgejo，带 RSS + API | k8s.af 的上游已迁至此 |
| `gitee.com/mirrors` | 2.8 万+ GitHub 镜像，每日同步 | 中文线路的 GitHub 兜底 |
| `gitcode.com` | `gitcode.com/GitHub_Trending/<owner>/<repo>` | 同上 |
| HN Algolia API | `https://hn.algolia.com/api/v1/search?query=...&tags=story` | **HN 站点 HTML 抓不到，但 API 可用**——发现层走 API 而非爬页面 |
| `lobste.rs/hottest.json` | JSON feed | 发现层 |
| `danluu.com`、`increment.com/feed.xml`、`k8s.af`、`microservices.io/patterns/` | 直接可达 | 高信号经验源 |

**对本设计的直接含义**：P4（经验采集管线）的**发现层应当是"API + JSON feed 优先"，而不是网页抓取**；同时对每条透镜强制记录 `collected` 日期——因为**没有 Wayback 兜底，链接腐烂不可恢复**，只能靠我们自己留痕。

### A.2 许可分级（决定"哪些能随开源工具分发"）

这是附录里**最具约束力**的一节。先看一个在真实素材上立刻踩到的例子：`microservices.io` 的模式目录是体验型透镜的高价值素材，但版权标注是 **"All rights reserved"**（另有官方中文版 `/patterns/cn/`）——所以**不能把它的模式描述搬进透镜正文**，只能"引模式名 + 用自己的话写检查问题 + 存 URL 与访问日期"。

分三级，入库时必须标注级别。

**① 可再分发（许可明确）** —— 可以随仓库分发，但仍建议保留出处与许可声明：

| 资产 | 许可 |
| --- | --- |
| NIST SSDF SP 800-218 | 公有领域（零许可风险） |
| Google eng-practices | CC-BY-3.0 |
| Google AIP | CC-BY-4.0 |
| OWASP ASVS 5.0.0 | CC-BY-SA-4.0（**注意 ShareAlike 传染**：衍生作品需同许可） |

**② 禁止再分发（All rights reserved）** —— **只能提炼事实 + 存链接，不得搬运正文**：
`microservices.io`、`refactoring.guru`、`12factor.net`、`martinfowler.com`、`SEI`（需书面许可）、美团技术 / 腾讯云 / 阿里云社区。

**③ 禁演绎** —— 阮一峰博客为 **CC BY-NC-ND 3.0**：可链接、可引用事实，**不可改写**。这一条与我们的蒸馏工序直接冲突，此类来源只能作为"线索"，透镜正文必须另行取证。

**安全实践（写成硬规则）**：仓库内只存 **链接 + 结构化 metadata + 我们自己的 paraphrase**；**第三方全文、长引文、第三方 embedding 一律不入库**。需要原文时，由运行时在用户侧抓取，结果不落库。这条同时解决了版权与"透镜库变成过期博客堆"两个问题。

> **一处必须修正的引用错误**：文本与数据挖掘（TDM）的 opt-out 条款在 **DSM Directive (EU) 2019/790 Art. 4(3)**，**不在** EU AI Act Art. 4（后者是 AI literacy）。凡在治理文档中引用 TDM 例外，必须按前者写，二者不可混引。

### A.4 失败模式的量化实证（可直接建表，且已回答"值不值得做"）

| 来源 | 结论 | 对本设计的用法 |
| --- | --- | --- |
| *Metastable Failures in the Wild*（USENIX ;login:, 2022），逐篇分析数百份公开事故报告 | 识别 21 起 metastable failure：**~45% 触发源是工程师错误/潜伏 bug；~35% 是负载尖峰；>50% 的 sustaining effect 是 retry policy；>55% 靠 load shedding 才恢复**。停机 1.5–73.53 小时，最常见 4–10 小时（35%） | 直接支撑 L3.2（重试风暴）与 L3.4（过载/卸载）成为**强制覆盖域**（§5.2 的缺口域规则） |
| Dan Luu 的统计 | 搜索 "global outage postmortem" 约 **50% 由配置变更引起** | 支撑"配置漂移/部署变更"类透镜的权重 |
| OSDI'14, Yuan et al. | ~200 个 bug 中 48 个 critical failure，**92% 源于错误处理代码** | 支撑"错误处理路径"必须作为独立透镜，而非附带检查 |

**这三条让"分类别的架构筛查确实指向真实故障分布"从直觉变成了有数据的主张**——也回答了 roadmap 里"值不值得投"的问题：透镜库的覆盖域可以按故障分布加权，而不是拍脑袋。

### A.6 工具链与既有生态缺口

**分发/聚合**：`Miniflux`（单 Go 二进制、真实 REST API、Google Reader API 兼容）最适合作发现骨干。FreshRSS 为 AGPL-3.0（捆绑时需注意）。Feedly / Inoreader API 属专有且 ToS 限制内容再分发 → **仅运行时**。

**蒸馏/校验**：`DSPy`（声明 "spans → claims" 签名并针对指标优化，概念上最契合）、`instructor`（Pydantic 校验的结构化输出 + 重试）、`Outlines`（受限解码，构造上即 schema 合法，极适合 span 抽取 pass）、`promptfoo`（断言式 eval，CI 友好）、`Ragas`（faithfulness / context-precision 直接对应 groundedness 要求）。

**KB CI**：`lychee`（事实上的最佳链接检查器）、`vale`、`ajv`、`markdownlint-cli2`。

> **⚠️ 生态缺口结论**：**没有以"源 provenance 优先"为设计的 LLM 知识库工具。** RAGFlow / Khoj / AnythingLLM / private-gpt / Verba / GraphRAG / LightRAG / nano-graphrag **全都假设"你自己持有语料"**——即它们存储 chunk，属于 §6.2 的 (e) 类。它们**只应作为用户可指向本地语料的可选后端，绝不能成为随附产物**。

**版本化**：Git 是默认选择（内容寻址、可评审、可 blame）。per-lens SHA-256（**覆盖规范化 JSON，排除易变时间戳**）用于检测语义漂移。KB 的 semver 定义：`MAJOR` = 已发布 lens 或 claim 被删除/被推翻（消费者必须重读）；`MINOR` = 新增；`PATCH` = 仅 provenance/freshness/metadata。机读 `lens-history.json` 让下游能问"自我 pin 的版本以来变了什么"。⛔ **DVC / lakeFS 在此是过度设计且方向错误**（它们为大型二进制数据集而生；本 repo 是文本 + 小 JSON）。
